## 2026-11-02

- **焦点**：闭环每步默认「观察中（截屏）」不合理；观察方式要覆盖脚本 / 代码 / 截图等，并由大模型按多维评分选取。
- **要点**：
  - 实操时间线：查服务是否在跑、Cursor 是否在跑时，仍先截屏；随后才用 `shell`/`ps`——截屏对「进程/端口」类目标准确率低、延迟与权限成本高。
  - 现状根因：`WorkerLoop` 在 `Brain.plan` 之前固定调用 `observe()`（截屏）；能力提示写明「观察截屏由闭环自动调用」。
  - 原则（用户给定）：在必要硬限定某种方式的前提下，对候选观察方式综合 **准确性（任务达成率）**、**及时性**、**运行成本**；**选取须大模型接入**，不可只靠关键词硬路由。
  - 范围：观察侧选型（采什么证据），与 [完成任务](../完成任务/结论.md) 的动作选型互补；不替代控制层执行。
- **本轮对结论**：新建本议题；写入已定原则、方式目录骨架、闭环改法方向、可行性速览；总表与术语表同步。未写入 `功能/`（未明示放行）。

## 2026-11-02（LLM 先选观察 + 工具结果观察）

- **焦点**：用户定调——LLM 输出观察方式再规划动作；调用工具后必须观察工具结果；超大输出（如数十 MB 日志）要智能取证，禁止整段塞进上下文。
- **要点**：
  - 闭环语义顺序钉死：**选观察 → 采观察 → 规划动作 → 执行 → 观察工具结果 →（再规划）**；「再」表示先后，不是允许跳过取证直接副作用。
  - **环境观察**（截屏/工作区/脚本）与 **工具结果观察**（stdout/文件内容/探仓命中）同属观察职责：都要判定「这段证据对当前子目标够不够、该留什么」。
  - 现状缺口：`_format_exec_feedback` 对 stdout/content **硬截 2000 字**——日志几十 MB 时既丢尾部报错，又可能把无关噪声当主证据；progress 与 history 同源裁剪，模型易误判。
  - 智能取证原则（待落地）：先量体（体积/行数/是否像日志）→ 按目标抽（尾部错误、关键词、头尾窗、结构化摘要）→ 超阈值再二次压缩；禁止默认「只留前 N 字」。
  - 同调 vs 两调：用户强调「先观察再规划」语义；实现可仍一次 LLM 产出 `observe`+`actions`（本步动作基于**上轮已观察的工具结果**），或拆两调；开放项收敛为推荐形态。
- **对结论**：改闭环形态为含工具结果观察；补已定条与可行性行；开放 P0 收敛；总表同步。未改 `功能/`（未明示放行实现）。
