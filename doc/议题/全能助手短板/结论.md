# 结论

## 议题

自建对标 Claude Code + 腾讯 WorkBuddy 量级的 PC/手机全能操作助手时：用户最想要的能力是什么、底层短板卡在哪、按什么依赖顺序攻。

## 已定结论

1. **北向目标**：用户侧效果对标「桌面/手机上把活干完」的全能助手（Claude Code 级编码与工具闭环 + WorkBuddy 级办公执行与可验收交付），双端任务可托管；不以「聊天答疑」为终态。
2. **能力四件套（用户当前最想要；按依赖排序，不是按愿望强度）**：

   | 序 | 能力 | 一句话验收 | 依赖 |
   |:---|:---|:---|:---|
   | C1 | **LLM 接入** | 可稳定对话、带工具调用协议（function/tool call） | 无 |
   | C2 | **完成任务（含能力自知）** | 能拆任务；能判断「自己现在能不能做」；能在工具 / 本地软件 / 外部服务间选型；做不到则明示边界而不是瞎点 | C1 |
   | C3 | **自主操控 PC/手机** | 在授权范围内观察界面并执行操作，且能回证成败 | C1；与 C2 强耦合（选型决定走 GUI 还是结构化工具） |
   | C4 | **自我进化** | E1：轨迹→Skill/教训（质量门）；E2：规划执行下改当前代码/文档并产品升版（禁改归档评测与 versioning 源码） | C2 可记录结构化轨迹即可开；**不堵 C3**（细节见 [自我进化](../自我进化/结论.md#已定结论)） |

3. **愿望 vs 攻关**：四件套都是目标；**当前真正难、且决定「不亚于竞品」体感的**，仍是：
   - **短板 A（撑起 C3，并反哺 C2）**：操控接地 + 回证（L2/L3）。
   - **短板 B（撑起 C4）**：记忆与进化闭环（L5），不是「接了个向量库」。
   - C1 本身**不是**短板（API/SDK 成熟）。
   - C2 常被低估：没有「能力清单 + 选型策略」，C3 会沦为默认乱点 GUI；C2 的核心是**路由与边界**，不是再堆模型。
4. **任务并发约束（与 [操作分身三层](../操作分身三层/结论.md#已定结论) 对齐）**：
   - **一总管 + 多解耦工作任务**。
   - **前台（鼠标/键盘/前台 GUI）：只串行**。
   - **后台：默认可并行**；凡会**修改**的后台资源必须先报**资源清单**，清单冲突由**总管协调**（串行/改址/推迟等）。
   - L4 第一天按此设计；禁止单会话线性脚本假装多任务；禁止未申报写后台。
5. **推荐落地顺序（里程碑）**：
   - **M1**：C1 接通（多模型可切换可选）。
   - **M2**：C2 窄域 + **≥2 后台任务并行**；其中至少一例验证「写资源清单冲突 → 总管仲裁」。
   - **M3**：C3 窄场景 + **前台 lease 硬串行**（排队持锁，同时仅一个任务动键鼠）。
   - **M4**：C4 初版——**可不堵 C3**，结构化/会话域先做；E1 轨迹复盘 → Skill/教训 + 写入红线；E2 自升级（快照闸门 + 禁改名单）；全自动棘轮后置。可与 M3 **并行**。
   - 双端手机：默认 **M3 在 PC 达标后再开**，除非用户另行指定同里程碑。
6. **底层栈（自下而上；短板落点）**：

   | 层 | 内容 | 成熟度 | 主要服务 |
   |:---|:---|:---|:---|
   | L0 | 设备 I/O：键鼠、触控、adb、文件/shell | 高 | C3 |
   | L1 | 观察：UI 树 / OCR / VLM | 中高 | C3 |
   | L2 | 接地运行时：意图→定位→动作→结构化回传 | 低～中 | C3 / 短板 A |
   | L3 | 回证与恢复 | 低 | C3 / 短板 A |
   | L4 | 任务与事件（总管；前台串行；后台并行+写清单仲裁） | 中 | C2 多任务 |
   | L5 | 记忆与进化 | 低 | C4 / 短板 B |
   | L6 | 产品壳 | 中 | 后置 |

7. **与「三层+两线」映射**（见 [操作分身三层](../操作分身三层/结论.md#已定结论)）：
   - C1+C2 → **大脑**（总管编排脑 + 任务执行脑；能力判断与工具/软件选型）
   - C3 → **观察 + 控制**，质量取决于 L2/L3；受租约约束
   - C4 → **知识经验线**（E1）+ 任务线承载的自升级（E2）；见 [自我进化](../自我进化/结论.md#已定结论)
   - 任务线 = 总管与并发的载体，贯穿 C2～C4
8. **竞品对照（公开信息，已核定位 / 未核实测效果）**：
   - **Claude Code**：C1+C2+结构化执行极强；C3 全 GUI 非主场；C4 偏会话/项目内，非通用桌面进化。
   - **WorkBuddy**：C1+C2+文件/专家/Skill/连接器公开强调强；多任务并行有公开叙述；C3 任意 GUI 是否已解 **未核**；C4 棘轮 **未核**。
9. **明确不做（本议题）**：不敲定具体模型厂商与 JSON schema；本仓不维护 `doc/or/`（本结论即需求真源，开工须明示执行）；不以「换更大模型」替代 C2 路由或 C3 接地；不承诺前台键鼠并行；不承诺未报清单的后台乱写。

## 依据摘要

- 四件套是产品愿望清单；依赖上必须先能想清楚选什么手段（C2），再谈点得准（C3），再谈越用越强（C4）。
- 同一 LLM 在结构化工具环境「聪明」、在无路由的 GUI 上「傻」——故 C2 的能力自知与选型，和 C3 的接地同等关键。
- RPA（L0）成熟只保证「能点」，不保证「该不该点、点谁、点成没有」。
- 无轨迹与质量门的「自我进化」只会污染 C2 的选型记忆。
- 前台物理互斥 → 串行；后台吞吐靠并行，正确性靠**写资源清单 + 总管仲裁**。

## 可行性速览

口径：**全 AI 实现**；粗估、未核价；不等于开工。

| 想法 | 难易（对 AI） | 成本与时间（粗） | 可借用资产 |
|:---|:---|:---|:---|
| **C1 LLM 接入**（对话 + tool call） | **低**。难点：密钥与多模型适配、流式与超时 | **落地**：约 **1～3 次**会话 / **约数小时墙钟**。**运行**：按 token。**人机闸门**：无（账号自备） | **可直接用**：OpenAI/Anthropic/国内兼容 API；LiteLLM 等路由（需适配） |
| **C2 能力自知 + 工具/软件选型** | **中高**。难点：能力清单要机读；「做不到」要敢拒绝；GUI vs 文件/API 路由策略易漂 | **落地**：注册表+策略 MVP 约 **4～10 次**会话 / **约 0.5～1.5 日墙钟**；与评测集对齐再加 **3～6 次**。**运行**：每步规划 LLM | **可直接用**：function calling。**需适配**：MCP / 自建 tool registry。**仅参考**：Claude Code 工具面、WorkBuddy Skill/连接器形态 |
| **L4 总管 + 后台并行 + 写清单仲裁 + 前台串行** | **中高**。难点：清单归一化与漏报；前台硬闸门 | **落地**：后台并行+冲突检测约 **4～8 次** / **约 0.5～1.5 日**；前台 lease 约 **2～5 次**。细节见 [操作分身三层](../操作分身三层/结论.md#可行性速览) | 队列 + SQLite 资源锁表 |
| **C3 自主操控 PC/手机（L2+L3）** | **高**。难点：定位稳定、回证；必须持 foreground_lease | **落地**：单 App 闭环约 **10～25 次**会话 / **约 1.5～3.5 日墙钟**。**人机闸门**：辅助功能/adb | AX、UIAutomator、`adb`、`pyautogui`；VLM 兜底 |
| **C4 自我进化（E1+E2；不堵 C3；棘轮后置）** | **中高→高**（棘轮与自改代码更高）。难点：脏写；禁改名单；升版评测纪律 | **落地**：E1 约 **3～8 次**；E2 约 **5～12 次**；棘轮再 **8～20 次** / **约 2～4 日墙钟**。细节见 [自我进化](../自我进化/结论.md#可行性速览) | `fs_*`/`version_*`；文件 Skill 库；darwin-skill 仅方法论参考 |
| **双端对齐** | **中高** | PC M3 后再做；量级约翻倍 | 语义统一、适配层分叉 |

**横切**：M2 验收「≥2 后台并行 + 一例写清单冲突被总管拦住/串行」；M3 验收「前台键鼠同时仅一任务 + 成功率可统计」。
