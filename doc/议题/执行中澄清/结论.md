# 结论

## 议题

在默认「尽最大努力完成」的任务闭环上，用户目标或上下文不全时，如何允许大脑**暂停并向用户提问 / 给出选项**，避免硬猜造成不可逆坏结果，同时不把「凡歧义就问」变成默认打断。

## 已定结论

1. **定位（已定）**：规范名 **执行中澄清**。挂在单次 `WorkerLoop` 规划结果之后：大脑可产出 `status=need_input`，任务进入 `waiting`，会话出澄清卡；用户在**同一任务线程**回复后注入答案并续跑。**不等于** [任务复盘](../任务复盘与管理/结论.md#已定结论) 的放行/勾选，也**不等于**终态追问路由里的 continue/new_task 拆任务。
2. **与「尽最大努力」关系（已定）**：
   - **默认仍尽最大努力**：能查工具、能从工作区/历史合理推断的，继续 `continue`，禁止无故打断。
   - **打断门槛（1A）**：仅当继续猜会有明显坏结果时才 `need_input`——不可逆写/删、提交、外发、花钱、互斥执行路线必选一等。
   - 缺信息但风险低（展示性措辞、可事后改的草稿路径）→ 选合理默认并在 `thought` 简述假设，不问。
3. **提问形态（已定，2A + 选择题优先）**：
   - 首期**不要求**可点按钮；用户在线程打字回复即可。
   - **已有明确互斥选项时必须出选择题**：Plan 带 `options: [{id,label}, …]`（≥2）；文案引导「请回复编号或标签」，禁止改写成开放式「请描述你想怎样」。
   - 尚无清晰选项、但确属 1A → 允许纯问句（无 `options`）；能先用工具探清选项的，先探再问。
4. **协议（已定，放行后实现）**：

   | 环节 | 行为 |
   |:---|:---|
   | Plan | `status=need_input`；`thought`=给用户看的问句；可选 `options`；`done=false`；`actions` 必须空 |
   | Worker | 出站 `Message.card`（`meta.phase=clarification`，含 question/options）→ `meta.clarification={phase:awaiting_input,…}` → `set_waiting` → 落检查点 → **结束本轮 run**（不 fail / 不 complete） |
   | Hub | `waiting` 且 `clarification.phase=awaiting_input`：本条入站视为答案（**不**走 `route_followup` 拆新任务）→ 注入 history（及可读摘要并入 goal）→ 清 awaiting → 拉 Worker 从检查点续跑 |
   | 进程续跑 | `awaiting_input`（及复盘类 waiting）**跳过**自动拉 Worker；仅用户回复路径拉起 |

5. **提示词约束（已定）**：注入「默认尽最大努力；仅 1A 用 need_input；有清晰选项必须填 options」。能力清单外目标仍可 `failed`；澄清不能用来绕过清单假成功。
6. **PWA 首期（已定）**：card 渲染问句 + 编号选项列表；用户回 `1` / 选项标签 / 短 id 即算选择。可点按钮为后续增强，不挡 MVP。
7. **明确不做（本议题）**：
   - 「凡歧义就问」作默认
   - 首期强制可点 UI、多轮问卷引擎、另造任务状态名（不用新 status；复用 `waiting` + meta）
   - 与复盘 `awaiting_approval` / `awaiting_apply` 共用同一 meta 字段

## 依据摘要

- 现网规划只有 `continue|success|failed`，信息不全时只能硬猜或失败；复盘已验证「waiting → 对话回复 → 再跑」可行。
- 用户定调：1A 门槛 + 2A 打字回复；有明确选项时优先选择而非开放作答。
- `RECOVER_STATUSES` 含 `waiting`；若不跳过 `awaiting_input`，重启会在无人回答时继续推进，抵消澄清。

## 可行性速览

口径：**全 AI 实现**；粗估、未核价；不等于放行或开工。

| 想法 | 难易（对 AI） | 成本与时间（粗） | 可借用资产 |
|:---|:---|:---|:---|
| **Plan `need_input` + 提示词门槛** | **低～中**。难点：模型仍爱乱问或乱猜；靠提示 + 轻校验（有 actions 则拒） | **落地**：约 **1～2** 次会话。**运行**：无额外模型调用（同规划轮） | **可直接用**：`brain/planner.py` status 解析；能力校验模式 |
| **Worker waiting + 澄清 card + checkpoint** | **低～中**。难点：停环不标 failed；meta 与复盘字段隔离 | **落地**：约 **1～2** 次会话 | **可直接用**：`Supervisor.set_waiting`；`Message.card`；`dump_checkpoint` |
| **Hub 答后续跑（跳过 route_followup）** | **中**。难点：与 review waiting、running 追加分流；答案解析（编号/标签） | **落地**：约 **2～3** 次会话 | **可直接用**：`hub` 复盘特判旁路；`requeue`/Worker 拉起 |
| **续跑跳过 awaiting_input** | **低**。难点：与复盘 waiting 一并过滤，避免误拉 | **落地**：约 **1** 次会话 | **可直接用**：`recover_interrupted_tasks`；`RECOVER_STATUSES` |
| **PWA 编号列表（无可点）** | **低** | **落地**：约 **1** 次会话 | **可直接用**：现有 card 气泡渲染 |
| **冒烟：need_input → 回复编号 → 续跑成功** | **低～中** | 约 **1** 次会话 | **可直接用**：`demo_review` waiting→回复模式 |

## 开放问题

| 优先级 | 问题 |
|:---|:---|
| P2 | 用户回复既不像编号也不像标签时：再贴一次澄清卡，还是当自由文本直接注入续跑？（建议首期：自由文本注入并在 history 标明「未匹配选项」） |
| P2 | 澄清等待是否设超时自动 fail / 提醒？（建议首期不做超时） |
| P3 | 可点选项按钮是否与会话 Diff confirm 同一套交互控件？ |
