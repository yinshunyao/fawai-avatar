# 结论

## 议题

fawai-avatar 作为 PC/手机操作分身，主能力如何分层，以及与之正交的贯穿能力是什么；任务线采用何种并发形态。

## 已定结论

1. **产品定位**：面向 PC/手机的操作分身——理解用户任务，观察界面状态，规划并执行操作，评估结果；任务可跟踪，经验可沉淀。
2. **能力三层**（职责互不替代）：
   - **大脑**：理解与规划任务；形成指令（做什么、调用哪些工具与代码）、脚本与代码；形成面向 PC/手机的动作指令；评估任务进展并给出结论。
   - **控制**：按指令调用工具、执行脚本与代码；操作鼠标与键盘；向大脑/上层返回执行结果。
   - **观察**：采集并理解屏幕操作与界面状态，解析为 LLM 可理解的内容（路径可含 OCR，不限于 OCR）。
3. **两条贯穿线**（与三层正交；各层可读写，但不自成「执行层」）：
   - **任务与事件管理**：任务生命周期、进度与状态；事件触发与调度（创建/暂停/恢复/完成/失败、外部唤醒）；回答「现在在跑什么、卡在哪、下一步何时动」。
   - **知识经验存储**：可复用做法、失败教训、场景与操作经验；供大脑规划与评估时检索；执行与复盘后可回写，避免同一坑反复踩。
4. **任务形态（已定）：一总管 + 多解耦任务可并发**：
   - **总管（Supervisor）**：面对用户的唯一编排入口——接需求、建任务、调优先级、暂停/取消、汇总进展；并做**资源冲突仲裁**；**不**把所有任务的逐步执行塞进同一段对话上下文里串着跑。
   - **工作任务（Worker Task）**：彼此**解耦**——各自目标、状态机、上下文/轨迹切片、规划回合；完成/失败只通过任务线回传总管，不互相直接改对方内部状态。
   - **并发含义**：多个工作任务可同时处于活跃（running / waiting / blocked）；调度由总管+任务线事件驱动。
   - **大脑角色**：总管侧可有「编排脑」；每个工作任务侧有「执行脑」跑观察→规划→控制闭环。二者职责分离，禁止一个巨型上下文兼任所有任务逐步点击。
5. **资源并发规则（已定，强制）**：
   - **前台操控：只串行，不并行**。凡涉及**鼠标、键盘、触控、前台焦点 / 前台 App GUI** 的操作，全局同时最多一个任务持有；其它任务排队或 blocked。控制层须硬闸门，不得靠模型自觉。
   - **后台：默认可并行**。不占前台键鼠的任务（如下载、API、纯计算、只读扫描、无焦点后台脚本等）可同时跑。
   - **后台可写资源须报清单**：任务在申请执行（或规划稳定后）须向总管申报**拟修改的后台资源清单**（例：文件/目录路径、数据库/表、端口、账号会话、指定后台进程、共享队列名等；只读可不报或标 `read`）。未申报的写入视为违规，控制层应拒绝或升格总管。
   - **冲突由总管协调**：清单相交且至少一方为写（写写 / 写读策略待钉）→ 总管仲裁（串行化、改路径、推迟、取消、请用户裁夺）。无交集则后台继续并行。
   - **两类锁**：`foreground_lease`（前台键鼠，全局唯一）与 `resource_lease`（后台可写资源，按清单项）；总管统一记账。
6. **运行关系**：
   - **单任务执行闭环**：观察 → 大脑 → 控制 → 再观察。
   - **多任务**：总管 ↔ 任务线事件 ↔ 各任务自有闭环；知识线跨任务只读共享、写入按质量门。
   - 边界：大脑不直接摸输入设备；控制不负责任务级编排；观察不擅自改系统状态；两线不替代控制做副作用、不替代观察读屏；**工作任务不绕过总管占用前台锁或未申报写资源**。
7. **明确不做（本议题范围）**：
   - 不在此敲定具体模型、框架、指令 JSON schema，或任务/知识的存储库表细节
   - 本仓不维护 `doc/or/`；本结论「已定结论」即需求真源，开工须另行明示「实现/执行」
   - 不承诺前台键鼠并行；不承诺「未报清单也可随便改后台」

## 依据摘要

- 操作分身的价值在「看懂界面 → 想清楚下一步 → 真正点得动/敲得出 → 再确认做没做对」；缺任一层都无法闭环。
- 多任务、异步唤醒、长流程若只活在单次对话里，无法并发与恢复；故要总管+解耦任务，而不是单会话线性脚本。
- 前台键鼠是物理互斥；后台并行的主要风险是**写同一资源**——故用申报清单 + 总管仲裁，而不是禁止一切后台并行。
- 三层管「这一步怎么做」；两线管「事归谁管、经验从哪来」；总管是任务线上的编排与资源仲裁角色，不是第四执行层。

## 可行性速览

口径：**全 AI 实现**（编码 Agent + 模型 API）；粗估、未核价；不等于开工。禁止人天主口径。

| 想法 | 难易（对 AI） | 成本与时间（粗） | 可借用资产 |
|:---|:---|:---|:---|
| **大脑**（规划/指令/评估） | **高**。难点：工具选择与幻觉指令；长任务拆步评测；失败恢复 | **落地**：窄场景闭环约 **8～20 次**会话 / **约 1～3 日墙钟**。**运行**：每步 LLM。**人机闸门**：无 | 主流 LLM API；LangGraph / AutoGen 类循环需适配；`AutoCore` 仅参考 |
| **控制**（工具/脚本/键鼠） | **中高**。难点：权限、焦点、双端分叉 | **落地**：单端 MVP **4～10 次** / **约 0.5～1.5 日**；双端量级翻倍。**人机闸门**：辅助功能/adb | AX、`pyautogui`、adb/UIAutomator；Playwright（Web 子集） |
| **观察**（屏幕→LLM 可读） | **中高**。难点：DPI、路由 OCR/树/VLM | **落地**：MVP **4～8 次** / **约 0.5～1 日**；加 VLM 路由再 **3～8 次** | PaddleOCR、AX/dump、VLM API |
| **任务与事件（单任务状态机）** | **中** | **落地**：**2～5 次** / **约数小时～1 日** | SQLite/文件表 |
| **总管 + 多解耦任务并发** | **中高**。难点：任务隔离；事件总线；总管与执行脑边界 | **落地**：后台并行骨架约 **4～8 次**会话 / **约 0.5～1.5 日**。**运行**：总管偶发 LLM + 各任务 LLM。**人机闸门**：无 | 进程内队列 + SQLite；asyncio/ARQ 需适配；Temporal 早期过重 |
| **前台串行闸门（foreground_lease）** | **中**。难点：控制层强制持锁；超时释放；任务切换不丢状态 | **落地**：约 **2～5 次**会话 / **约数小时墙钟**（在控制层加锁）。**运行**：无额外模型费 | OS 互斥锁 / 进程内 lock；与键鼠调用同一路径包一层 |
| **后台可写资源清单 + 冲突仲裁** | **中高**。难点：清单粒度与归一化（路径/通配）；漏报；读写冲突策略；动态加申资源 | **落地**：声明式清单+交集检测 MVP 约 **3～7 次**会话 / **约 0.5～1 日**；含漏报拦截与动态追加再 **3～6 次**。**运行**：仲裁可先规则、难例再调 LLM | **可直接用**：资源集合表 + 锁。**仅参考**：数据库锁/租约、文件系统 flock 思想 |
| **知识经验存储** | **中**。难点：脏写、粒度 | **落地**：文件库 **2～4 次**；向量再 **4～8 次** | 结构化文件；Chroma/sqlite-vec 需适配 |

**横切**：先「后台可并行 + 写资源清单仲裁 + 前台强制串行」；再谈前台抢占优先级。与 [全能助手短板](../全能助手短板/结论.md#已定结论) 的 M2/L4 对齐。
