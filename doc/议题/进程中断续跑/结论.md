# 结论

## 议题

服务重启后，工作任务如何诚实续跑：状态仍在、进程内 Worker 已死时，既不假「执行中」空挂，也不整任务从零重跑。

## 已定结论

1. **策略（已定）**：启动自动续跑（原方案 B），但**禁止**默认 `requeue → pending` 当恢复手段。
2. **续跑语义（已定）**：靠 **`meta.run_checkpoint`** 保存闭环可变状态（history、next_step、计数器、守卫指纹等）；新进程 `WorkerLoop.run` 若有检查点则从 `next_step` 接着规划，**复用同一 `run_id` 时间线段**。
3. **启动扫描（已定）**：
   - `running` / `waiting` / `blocked` → 拉 Worker 续跑（有检查点则续，无则相当于从当前 goal 接着跑第一步）。
   - `pending` → 拉 Worker 首次执行（本来就未开跑）。
   - `paused` → **不**自动拉起；用户恢复后再跑。
4. **恢复口令（已定）**：`resume` 将 `paused→running` 后，若该任务**无存活 Worker 线程**则补拉；同进程内暂停等待中的线程仍在 → 只改状态，禁止双开。
5. **检查点时机（已定）**：每步迭代成功收束后写盘；进入协作暂停前写盘；任务 `_finish` 清除检查点。
6. **明确不做（本切片）**：不保证单次 LLM/shell 调用中途强杀后续精确半步回放；不跨机调度；不把已完成终态自动重开。

## 依据摘要

- 状态在 SQLite，执行在 daemon 线程；保活/热重载只复活网关。
- 用户否决「重新跑」：续跑须带着 history，避免大脑当新任务再写一遍。
