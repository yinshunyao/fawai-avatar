# 结论

## 议题

规划轮如何按**本轮目的**裁剪系统提示与是否附带用户图/走 VLM，避免「附图后全程全量提示」导致输出截断与 token 浪费。

## 已定结论

1. **问题定性（已定）**：现网 `Brain._plan_once` 每轮注入同一套长 system（能力清单约一半体积）+ 目标附图则每轮重塞图并路由 VLM。任务后期已变成「读/改已知文件」时仍如此 → 易半截 JSON、`无法解析 JSON`。
2. **原则（已定）**：**有图 ≠ 全程 VLM**；图只服务「本轮需要看图」的目的。硬校验仍用全量能力清单；**提示词可按档只注入子集**。
3. **提示档（已定，首期四档）**：

   | 档 id | 何时 | 模型倾向 | 提示保留 | 砍掉 |
   |:---|:---|:---|:---|:---|
   | `vision` | 目标有附图且尚无工具回合 | VLM + 附图 | 短目标、平台一句、定位用 fs 子集、极短 JSON 格式 | 全量 when_to_use、GUI/Git/Skill 长文、编码上下文 |
   | `fs` | 文件/代码/前端改页类，或历史已有 fs 工具回合 | 文本（**卸图**） | `fs_*`/检索/check/git/skill 子集 + 定向读规则 | 用户附图、GUI 细则 |
   | `gui` | 目标明确依赖可见 App UI | 可截屏/VLM | GUI kinds + 前台/观察规则 | 大段编码/git 说明 |
   | `full` | 兜底 | 按是否有图路由 | 接近现网全量 | 无（仅加 thought 短约束） |

4. **thought 约束（已定）**：各档提示写明 `thought` 宜短（≤40 字优先）；先保证 `status`/`actions`/`observe_kinds` 完整，降低截断落在半字段上的概率。
5. **推断规则（已定，规则闸 + 可演进）**：首期用规则推断档（目标附图、是否已有工具历史、文件/前端/GUI 语义），**不**再加一轮 LLM 只为选档。开放问题里可后置「模型自报 profile」。
6. **明确不做（本切片）**：
   - 不改 `finish_reason` 续写 JSON（可另议题）。
   - 不把硬校验清单改成子集（防漏拦）。
   - 不做按厂商的特制 VLM 模板大爆炸。

## 依据摘要

- 任务 `7b9f3d2b`：前两轮 VLM plan 成功（↓≈230）；第三轮 ↓142 半截 JSON；prompt ≈6.9k；模型 `qwen3-vl-plus`；目标已落到 `index.html` 仍附带图。
- 现网 system 非编码约 6.9k 字，能力清单 alone ≈3.4k。

## 可行性速览

口径：**全 AI 实现**；粗估、未核价。

| 想法 | 难易（对 AI） | 成本与时间（粗） | 可借用资产 |
|:---|:---|:---|:---|
| **提示档模块 + 推断 + 接 planner** | **低～中**。难点：前端改页类目标要进 `fs` 档；卸图后文本仍够用 | **落地**：约 **1～2** 次会话。**运行**：降 VLM/prompt token | **可直接用**：`planner._system_prompt`；`capabilities_prompt_block`；`messages_need_vision` |
| **demo 断言档与体积** | **低** | 约 **0.5** 次会话 | mock history / 无真 LLM |
