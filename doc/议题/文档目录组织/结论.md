# 结论

## 议题

`doc/` 如何组织：取消 OR 后，用什么表达「允许实现 / 实际已支持」的功能面。

## 已定结论

1. **不用 OR / 不套全局规划树**：不建 `doc/or/`，不人工誊写需求树，不套 `01-or`～`99-ops`，**不建** `02-dr` / `03-tr` / `99-ops`。经确认的方案写入 `功能/{短名}/说明.md`（或 `分析/`），本仓文档树优先于 workspace 全局 plan-archive。
2. **双层文档（强制）**：
   - **`议题/`**：讨论与收敛——会话 + 结论（含可行性、明确不做、开放问题）。**不等于**已放行实现。
   - **`功能/`（功能目录）**：**放行实现与实际支持面的目录**——只登记「准做 / 正在做 / 已能用」的功能条目；实现与验收以这里为准。
3. **功能目录形态**：

```text
doc/
  AGENTS.md
  术语与称呼索引.md

  议题/                        # 讨论（已由 issue/ 改名）
    AGENTS.md
    【总表】议题一览.md
    {短名议题}/会话.md + 结论.md

  功能/                        # 功能目录（放行与已支持）
    AGENTS.md
    【总表】功能一览.md         # 唯一总表：一行一功能
    {短名}/                    # 可选；条目变复杂时再拆说明，勿预建空壳
      说明.md                  # 验收口径、边界、实现映射（短）
```

4. **【总表】功能一览.md 列约定**：

   | 列 | 含义 |
   |:---|:---|
   | **功能** | 短名（规范名，与术语表对齐） |
   | **状态** | `放行`（准实现未交付）/ `实现中` / `已支持`（实际可用） |
   | **要点** | 一两句能力边界 |
   | **来源** | 链到议题 `结论.md` 相关节（讨论依据） |
   | **代码** | 入口路径或「未落地」 |

5. **何时进功能目录**：用户明确说「放行 / 写入功能目录 / 可以做这个」等；或实现完成后登记为 `已支持`。助理**不得**仅因议题里写了已定结论就自动加功能行。
6. **开工依据**：实现只碰功能表里状态为 `放行` 或 `实现中` 的条目；输入 = 该功能说明（若有）+ 来源议题已定结论 + 术语表。做完改状态为 `已支持` 并填代码列。
7. **议题与功能的关系**：议题可以很多、可以否决；功能表保持短、可扫描——表示产品**实际承诺的能力面**。
8. **不再需要**：独立 OR；默认也不建 `架构/`（若某功能说明不够用，加长写在 `功能/{短名}/说明.md`，仍链回议题）。
9. **目录基建（已执行）**：`issue/` 已改名为 `议题/`；已创建空的 `功能/`（AGENTS + 空总表）；`doc/AGENTS.md` 与 Cursor 规则已对齐双轨。
10. **明确不做**：不建 `or/`；不用功能目录堆未放行想法；不把议题总表与功能总表合成一张（职责不同）。

## 依据摘要

- OR 的负担来自「再誊一套需求」；功能目录只回答「现在准做什么、已经有什么」，表格式、可扫。
- 议题保留争议与可行性；放行是显式闸门，避免讨论中的「已定」被误当成排期。
- 与术语表分工：术语管称呼与工具 id；功能目录管放行状态与代码入口。

## 可行性速览

口径：**全 AI 实现**；粗估、未核价。

| 想法 | 难易（对 AI） | 成本与时间（粗） | 可借用资产 |
|:---|:---|:---|:---|
| **建 `功能/` + 总表 AGENTS + 改 doc 根规则** | **低**（**已完成**） | 约 **1** 次会话 | 现有议题总表作模板 |
| **改名 issue→议题** | **低**（**已完成**） | 同回合 | 链接/globs |
| **首批功能行**（从已有议题挑放行项） | **低**。难点：哪些算放行须用户点名 | 用户点名后约 **1** 次会话 | 操作分身三层、全能助手短板 |
| **【总览】产品地图** | **低（可选）** | 有功能总表后可省略或缩成链到功能总表 | 功能一览 |
