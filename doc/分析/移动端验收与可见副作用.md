# 移动端验收与可见副作用

关联任务：`437588780c74476986ec8bc5b6b297db`（步骤列表手机 UI）。  
关联功能：[编码闭环](../功能/编码闭环/说明.md) 可见副作用闸；[浏览器操作](../功能/浏览器操作/说明.md)；[完成任务](../功能/完成任务/说明.md) 必要路径台账。

## 目标与终态

CSS/`@media` 已有写入后，模型改去 `app_focus` Chrome + 截屏「验手机」，失败后 `status=failed`，文案称缺乏视觉反馈、验证路径阻塞。

## 工具双栏

| 栏 | 结论 |
|:---|:---|
| **工具本身** | ① 可见副作用闸只卡「thought 是否说明可见变化」，**不要求**截屏；文案却易被读成必须实机验。② `browser_*` 原先无窄屏 viewport，模型更易退回桌面 Chrome。③ `app_focus` 成功 message 是 `activated Chrome`，模型又臆造 expect `ok: activated Chrome` → 假失败。 |
| **调用** | 把可选验收升成必要路径；用桌面截屏冒充手机 `@media`；反省 constraints 写「须验证否则 failed」。 |

## 必要 / 可选

| 槽位 | 类型 | 本案 |
|:---|:---|:---|
| 定位并 mutate 步骤列表样式 | 必要 | 已写入 |
| thought 说明可见变化 | 必要（闸门） | 可对照 diff 完成 |
| 实机截屏 / 浏览器打开验页 | **可选** | 被误升必要 → 阻塞 failed |
| 窄屏 viewport 下 browser 快照 | 可选（正确验法） | 当时未走；现已支持 viewport |

## 机制根因

1. **可选验收升必要** — 反省/台账未钉死「截屏属可选」。  
2. **验手机工具选错** — 桌面 Chrome ≠ 手机模式；缺 viewport 时更难走对。  
3. **可见副作用闸被误解** — 代码要的是可见变化叙述，不是强制视觉回证。

## 已落地

- `format_visible_effect_prompt`：标明可选验收；窄屏用 `viewport=mobile`。  
- `necessary_paths`：台账 + 清洗「须验证移动端/必须截屏」类 constraints。  
- `browser_navigate`：`viewport` / `mobile` / `{width,height}`。  
- 规划/能力清单提示对齐。

## 明确不做

- 不为「手机步骤列表」单开专用闸。  
- 不强制有头浏览器或系统 Chrome 调试器；无头+viewport 足够触发常见 `@media`。  
- 不取消可见副作用闸（仍拦假成功/占位 thought）。
