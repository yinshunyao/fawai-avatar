## 1. 当前状态（fawai）

### 1.1 三层约束（已落地）

| 层 | 机制 | 强度 | 代表实现 |
|:---|:---|:---|:---|
| **提示注入** | 每轮规划注入：能力清单、按目标命中的规则注册表（最多约 5 条）、Skill/lore 摘要、过程相位、编码/铲子话术等；可用规划提示档裁剪 | 软（靠模型） | `brain/planner.py`；`compliance.rules_prompt_block`；`prompt_profile` |
| **计划后校验** | 能力选型、架构 `doc_refs` / `architecture_skip_reason`；漏声明可自动绑定、软兜底、重规划 1 次 | 中～硬 | `capabilities.validate_plan`；`compliance.ensure_architecture_decls` |
| **闭环闸门** | 执行前后硬拦或注入重规划：路径禁改、租约、`shell_guard`、code_check、弱写入/可见副作用、探索/远端闸、【铲子优先】等 | 硬（真拦副作用）或软注入 | `runtime/loop.py`；`workspace/paths.py`；`control/shell_guard.py`；`brain/shovel_lifecycle.py` 等 |

产品口径（守规说明已写明）：**不承诺软规则 100% 被模型遵守；`hard` 与架构门 / 执行闸才硬拦。**

### 1.2 规则从哪来

| 来源 | 现状 |
|:---|:---|
| **规则注册表** | 代码常量 `brain/compliance.py::RULE_REGISTRY`（`id` / `when` / `constraint` / `hard`）；按 goal 关键词命中注入 |
| **功能说明 / 术语** | 人读真源；分层写须声明对应 `doc/功能/*/说明.md` |
| **能力清单** | 选型硬规则进提示；非法 kind / 文件目标用 GUI 等走校验 |
| **Skill** | 可检索步骤/教训；默认不做每任务自动蒸馏 |
| **fawai_shovels** | 可执行铲台账（三维分）；`shovel_search` + 写前/写后软闸 |
| **AGENTS / 仓内 rules 摘要** | 编码上下文软补充；**否决**默认全书灌多个 mdc |

与 Cursor 文件规则不同：fawai **新增一条可命中软规则**，通常要改注册表或规划提示 / 加闸，而不是只丢一个 `.mdc`。

### 1.3 跟规则的可靠度（现状定性）

| 规则类型 | 实际可靠度 | 说明 |
|:---|:---|:---|
| 不可逆边界（禁写路径、租约、shell 绕 fs） | 高 | 代码硬拦 |
| 编码回证 / 假 success / 补丁锚点 | 高～中高 | 多闸叠加；模型仍可能多绕几步 |
| 选型偏好、文风、先搜铲再造脚本 | 中 | 提示 + 软闸；软闸可关；硬闸默认关 |
| 未登记进注册表/闸门的「口头规矩」 | 低 | 等于没有 |

## 2. Cursor 侧（对照口径）

| 机制 | 含义 |
|:---|:---|
| `.cursor/rules/*.mdc` | `alwaysApply` 或按文件 glob 进入 Agent 上下文 |
| 工具台账类规则 | 多为提示纪律（先查 readme、三维分）；无统一产品级执行闸 |
| 主要约束方式 | **规则进提示 → 模型自觉**；纠错靠多轮对话或人工 |

强项：规则编写成本低、覆盖面易铺开、与「正在编辑的文件」绑定自然。  
弱项：多数规则**没有**与 fawai 同级的「计划后校验 + 写盘前硬闸」；违规常已发生副作用后再改。

## 3. 效果对照

| 维度 | fawai（当前） | Cursor（典型） |
|:---|:---|:---|
| 越权 / 不可逆写 | 强 | 弱～中（靠提示与习惯） |
| 编码闭环纪律 | 强（闸多） | 中（规则+习惯） |
| 软偏好遵守率 | 中 | 中（alwaysApply 时「常在眼前」，仍可无视） |
| 规则覆盖广度 | 窄而深（登记才稳） | 广（任意 mdc 可写） |
| 可测性 | 高（冒烟 / demo 闸门） | 低（难单测「是否遵守了某条」） |
| 规则作者体验 | 偏工程：改常量/闸/文档 | 偏文档：加 mdc 即参与提示 |

**总判：** 在「必须守住写盘与 shell 边界」上，fawai 强于 Cursor；在「廉价扩张大量软规范」上，Cursor 更轻。两者不是同一优化目标。

## 4. 成本对照

| | fawai | Cursor |
|:---|:---|:---|
| 单轮上下文 | 能力清单 + 命中规则 + 相位等；**刻意不全书灌 mdc**，体积相对可控 | alwaysApply / 多条长规则时，**每轮固定付** |
| 违规后 | 软闸/重规划 → **多 1～N 次 LLM 调用**；本地闸本身便宜 | 常一次做错再开一轮；无产品闸时副作用清理成本在人 |
| 延迟 | 闸触发时墙钟更长（observe→plan→act 加长） | 单轮往往更短 |
| 规则膨胀 | 命中上限 + profile 裁剪，扩规则相对可控 | alwaysApply 线性烧 token |

**总判：** 模型听话、任务简单时，Cursor 往往更省；模型偷懒或任务触及硬边界时，fawai 多付重规划，但少把坏结果落到盘上。

## 5. 改进思路（未放行；按优先级 vs 可选项分开）

下列均为**思路备忘**。要落地须开议题 → 用户明示写入功能目录。

### 5.1 必要方向（若立项，建议按序；后项仍属范围内，不是默认可砍）

| 序 | 方向 | 要解决什么 | 可能落点 |
|:---|:---|:---|:---|
| P0 | **规则外置加载** | 少改 Python 常量也能加软规则 | 注册表从 YAML/Markdown frontmatter 加载；仍保留 `hard` 与 when 命中 |
| P1 | **软规则效果可观测** | 不知道模型有没有「看见并遵守」 | 规划 meta / 复盘维：命中规则 id、是否触发对应闸、违规重规划次数 |
| P2 | **闸门成本仪表** | 重规划贵在哪 | 任务统计：闸种类、inject 次数、额外 LLM 轮次与 token；便于调默认开闭 |
| P3 | **软→硬晋升纪律** | 哪些软规则值得变硬闸 | 复盘高频违规 → 候选硬闸清单；禁止一上来全盘硬拦 |

### 5.2 可选（可砍；砍掉不影响「当前三层守规」成立）

| 方向 | 说明 | 风险 |
|:---|:---|:---|
| 接近 Cursor 的「按文件 glob 注入」 | 改某路径时自动多注入相关功能说明摘要 | 上下文膨胀；与「不全书灌」策略需配额 |
| 默认打开更多硬闸（如铲子硬闸） | 跟规则更死 | 延迟与失败率上升；简单任务变重 |
| 任务完成自动蒸馏规则/铲 | 进化更快 | 已否决默认自动蒸馏；仅适合显式复盘勾选 |
| 把仓内 `.cursor/rules` 整包镜像进注册表 | 作者体验统一 | 大量 alwaysApply 文会冲掉「命中 ≤5」的成本优势，需强制切片与评分 |

### 5.3 明确不建议（对照结论）

- 用「再堆更长系统提示」替代执行闸，指望软规则 100% 生效。  
- 默认把 Cursor 全量 Project Rules 灌进每一轮规划。  
- 为个案菜谱新开专用硬闸（与任务复盘「优化须通用」冲突）。

---

## 6. 一句话结论

**当前：** fawai 用「薄提示 + 计划校验 + 执行闸」跟规则，边界类可靠度高于 Cursor，软规则与 Cursor 同属「不保证」；成本上稳态可能略贵在重规划，贵在换安全与可测性。  

**以后：** 优先把规则作者体验（外置注册表）和闸门成本可观测做强，再谨慎把高频软违规晋升为硬闸；不要为了「更像 Cursor」牺牲「不全书灌 + 硬边界」这两条已定策略。
