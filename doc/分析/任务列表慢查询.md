# 任务列表慢查询

对照打开计划任务 / 侧栏刷新时的卡顿与 SQLite 访问形态。不等于功能放行。

## 现象（已核）

| 接口（本机网关，修前） | 体量 | 耗时 |
|:---|:---|:---|
| `GET /api/tasks?limit=50` | ~40KB | ~350ms |
| `GET /api/session` | ~177KB | ~380ms |
| `GET /api/tasks/{父计划}/history` | ~48KB / 数十条 | ~70ms |
| `GET /api/tasks/{子任务}` | ~1KB | ~2ms |

点开父计划线程时前端**先等 history 再画步骤**；同刻列表/详情还会再打任务库。用户体感「点了很久才有步骤」。

## 机制

1. **`meta.run_checkpoint` 膨胀**  
   步末把闭环 `history`/`traces` 整包写进 `tasks.meta_json`。长跑监管脑可达数十～数百 KB；库内另有已取消任务 checkpoint 达 ~400KB。全表 `SELECT *` 一次可读进数 MB JSON。

2. **N+1 全表扫描（主因）**  
   - `list_plan_child_ids` 旧实现：图上 id 之外再 `list_tasks(limit=200, archived=None)` 扫全表找 `plan_parent_task_id`。  
   - `_task_summary` 对每个 `orchestrator` 调 `plan_parent_stats_summary` → 再调 `list_plan_child_ids`。  
   - 列表 80 条里约 12 个编排父 → **约 12 次全表 SELECT \***，本地复现汇总约 **300ms+**；若只用标题/已有 `meta.stats` 则约 **2ms**。

3. **与写锁叠加**  
   子任务频繁 `UPDATE meta_json` 时，列表读与点开父计划的子任务发现会排队，尖刺更高。

4. **步骤「少/晚」的另一层**  
   进度信封挂在父 `task_id`；会话 soft-trim 后 `/history` 可能只剩近段；父无 `meta.steps` 时不回放。属可见性/完整性，不是本条慢查询主因。

## 已落地改动

| 层 | 改动 |
|:---|:---|
| `TaskStore` | `LIST_META_OMIT_KEYS`；`list_tasks(omit_meta_keys=…)` 用 `json_remove` 剔 checkpoint 等；`list_task_ids_by_meta_equals` 只回 id |
| `list_plan_child_ids` | 图上 id + JSON 等值查 id，**禁止**再全表 `list_tasks` |
| 列表 / session | `omit_meta_keys` + `_task_summary(live_plan_stats=False)`（吃父 `meta.stats`） |
| 详情 | 仍 `live_plan_stats=True` 现算子任务聚合 |

修后本地：`list omit` ~10ms；无 live stats 的列表摘要 ~2ms；`list_plan_child_ids` 均值约数毫秒。

## 仍可改进（未做）

| 项 | 说明 |
|:---|:---|
| checkpoint 体积闸 | 进一步压缩 `dump_checkpoint` 的 history/traces 上限；终态任务清掉无用 checkpoint |
| 表达式索引 | `json_extract(meta_json,'$.plan_parent_task_id')` 现仍 SCAN；任务量上千再考虑 generated column + index |
| 父计划 steps 回放 | soft-trim 后合并子 `meta.steps`（见问题清单条 2） |
