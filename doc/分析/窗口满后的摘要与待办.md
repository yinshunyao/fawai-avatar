# 窗口满后的摘要与待办

对照对象：上下文装不下全文时，执行循环怎么知道前面做完了什么。没有任务图时对照 Claude Code 的 compact、Cursor / Claude 的 Todo，以及 Deep Agents 的 `write_todos`。有任务图时对照节点状态和上下游产物。  
目的：钉清待办、compact、任务图各自留下什么。**不等于**功能放行。

## 1. 现状

简单目标没有任务图。规划每轮看到的是压缩后的对话：近窗默认 8 条、软上限 18000 字符。超限后，更早的工具结果收成「工具名 → 成败 + 路径」，助手想法收到约 120 字。仍超限就从最旧的摘要开始丢。

结论写在工具正文里。正文一掉，host、端口、铲子名、训练是否在跑，都不再进入下一轮。`read_windows` 记下了读过的行窗，规划前不注入。

计划模式的任务图已经有节点状态，并按依赖和租约调度。那张图只在判定进入计划模式之后存在。简单目标走单循环，进不了这张图。

## 2. 两份记忆各管一件事

公开产品在窗口满了以后不做「同一指纹执行前拒绝」。它们留下两份很小、且不被滑动窗口挤掉的记忆。

| 记忆 | 留下什么 | 下一轮靠它知道什么 |
|:---|:---|:---|
| compact | 做过什么、得到什么结论 | 这个事实还在不在，要不要再读正文 |
| 待办 | 待办 / 进行中 / 已完成 | 哪一步已经做完 |

只留待办、不留结论：条目可以是「已读配置」，下一步仍没有 host/port，还会再读，或在禁读提示下直接失败。  
只留 compact、不留待办：结论散在一段散文里；这段散文自己超限时，会和现在的远窗一样从最旧开始被丢掉，步骤身份跟着掉。

大结果外置是第三件相邻的事：单次工具输出太长时落成文件，上下文留路径和一行结论。它不代替 compact，也不代替待办。

## 3. 接到现有循环上

下列为必要项，编号只表示先后。第 2 项只用于没有任务图的循环。已接入现有规划循环和任务图；行为以功能说明为准。

1. **compact 换掉远窗机械摘要。** 触发条件沿用现在的超窗（条数或字符软上限）。用一次模型摘要替换「工具名 / 路径 / 成败」，写清做过什么、得到什么结论，并缓存在任务状态里，避免每轮重写同一段旧历史。近窗仍留原文。模型调用失败时，退回现在的机械摘要。有任务图时，节点内部仍用这套 compact。多节点共用的事实不靠这段摘要传递，见第 4.1 节。
2. **简单目标另维护一份小待办。** 状态只有待办、进行中、已完成。模型在同一轮里更新它。清单存在任务状态上，每轮单独注入规划，不放进会被压缩、被丢弃的历史消息，并写入检查点，续跑还能看见。条数和字数设硬顶，避免它变成第二份历史。已有任务图时不做这一份，节点状态即完成清单。

凭据不写入会反复注入的摘要和待办。此类结论只留「已从该路径取得，下一步用来连接」。下一步若确实需要明文，仍从文件读进环境，不从摘要里抄口令。

compact 不得把「曾经读过」写成「禁止再读」。结论不在摘要里时，定向再读仍是取证。这一点与 [禁读与工作记忆](./禁读与工作记忆.md) 同一边界。

## 4. 有任务图时

任务图上的节点状态已经是压不掉的完成清单：`pending` / `ready` / `running` / `completed` / `failed`。依赖完成且产物键已齐，调度才拉起下游。完成节点不会因为下一轮模型忘记而再拉一次。监管脑也不能改其它节点。这一层比模型自己维护的待办硬：它写在父任务的图上，不在会被压缩的历史里。

下游看不到上游的工具正文。监管脑目标只拼进本节点目标、停条件、用户总目标的前 500 字，以及 `consumes` 里每个产物大约 120 字。产物内容是该节点收尾想法的前 800 字，并抄到每个 `produces` 键上。

所以图记下的是哪一段做完了。这一段得到的 host、端口、训练是否在跑，只有写进那一截收尾才会传到下游。没写进去时，下游仍是一条自己的执行循环，远窗规则与简单目标相同，它会在自己的步里把上游的读取再做一遍。已完成节点本身不会被再调度。

有图时不另维护一份与节点平行的待办。两份状态会各写各的，调度仍只认图。compact 用在节点内部超窗，以及节点自己的收尾结论。凭据与「结论不在则允许再读」的边界，与简单目标相同。

节点内部的步级清单仍可有，但只记本节点授权里的步，不复述整张图。条数硬顶。步级清单不是有图时的必要项。

## 4.1 出图时标出共用信息

各节点会一起用到的事实，要在出图时由编排脑标出来。步级执行脑只看见本节点的历史，标不了「旁边那个节点也要这份 host」。编排脑出图时同时看见每个节点的目标，才能判断哪些信息会被多处用到。

现在的 `produces` / `consumes` 只是短键。键上的值是该节点收尾想法的前 800 字，注入下游时再截到大约 120 字。并行节点常常 `consumes` 为空，于是各自去读同一份配置。串行节点接到的是整段想法的截断，共用的 host、端口、任务标识夹在别的句子里，截断点一偏就失真。失真之后，下游只能再执行一次获取。

共用信息单独钉在图上，不走远窗，也不用整段收尾想法代替：

| 出图时定下 | 跑起来之后 |
|:---|:---|
| 事实叫什么（连接端点、训练任务、日志路径） | 只由一个节点生产 |
| 谁生产、谁消费 | 消费节点 `depends_on` 生产节点，调度在事实齐了之后才拉起 |
| 事实正文的存放 | 原文放在图上的该键；过长则落任务侧文件，注入时留路径和一行结论 |

消费节点的目标里注入的是这份原文（或路径加一行结论），不是上游收尾想法的前 120 字。节点看到事实已在，就不再为同一份信息执行获取。口令仍不抄进各节点目标，只记「已从该路径取得，下一步用来连接」。

出图时还看不到的事实，等生产节点做完再写入同一个键。键和消费关系必须在出图时就有，否则下游已经各自开工，写进去也来不及挡住重复获取。

## 5. 和待办的分工

任务图还管依赖、并行、前台租约、失败段重开。待办没有这些语义。Deep Agents 把 `write_todos` 做成可选，也是因为它只帮助同一条循环不丢步骤，不负责调度。

因此：

- 简单目标用 compact + 小待办。
- 已进入计划模式的目标用节点状态当完成清单。节点内部用 compact。多节点共用的事实由编排脑在出图时钉在图上，只获取一次，原文交给每个消费节点。
- 不在执行前按指纹拒绝重复动作。清单和结论还在，模型应自己避开已完成步；它们不构成硬闸。
