# 记忆与检索：业界思路对照

对照对象：fawai-avatar 的 **个人知识库 / Skill / 任务历史 / 仓检索**，相对业界 Agent 记忆与编码检索的常见架构。  
目的：回应「记忆和检索太弱」——钉清弱在哪一层、业界好思路是什么；**不等于**功能放行。

---

## 1. 先分清：弱的是「记忆系统」，不只是「搜得慢」

业界近两年反复强调一句：**Agent memory ≠ RAG。**

| | RAG | Agent 记忆 |
|:---|:---|:---|
| 主义务 | 从外部语料取证、 grounding | 跨回合/跨会话保留**可演化状态** |
| 写路径 | 通常人/管道更新语料 | Agent 或旁路要能 **写入、覆盖、失效、删除** |
| 难问题 | chunk、混合检索、引用 | **晋升、作用域、冲突、遗忘、溯源** |
| 向量库角色 | 基础设施 | 只是 archival 的一种索引，不是记忆策略本身 |

fawai 现在更像：**轻量 RAG 式注入 + 可写 KV/笔记/Skill**，但缺完整「分层记忆 + 生命周期 + 主动分页」。  
体感上的「记不住 / 找不着」会同时表现为：规划不带关键事实、多轮瞎 grep、同类错再犯。

## 2. fawai 现状（按记忆类型拆）

业界常用四分法（CoALA / MemGPT 同族）：**工作 / 情节 / 语义 / 程序**。

| 类型 | 业界要装什么 | fawai 现状 | 强弱 |
|:---|:---|:---|:---|
| **工作记忆** | 本轮 prompt 预算内：目标、近窗、注入块 | 系统提示 + lore/Skill/规则摘要 + 压缩 history | 有，但注入偏「关键词撞上才进」；预算与驱逐策略粗。正文被压掉后若仍禁再读，任务会被判死（见 [禁读与工作记忆](./禁读与工作记忆.md)） |
| **情节记忆** | 会话/任务轨迹可搜；驱逐前摘要 | 任务 history 落盘；规划用近窗+远窗摘要；**跨任务 recall 搜轨迹**弱 | 中偏低 |
| **语义记忆** | 事实/偏好/实体关系；时效与覆盖 | lore KV + 笔记；旁路抽取 + 缓冲人审 | **有写路径（亮点）**；检索弱（子串；向量仅笔记） |
| **程序记忆** | Skills / 规则 / 工具选用策略 | Skill 库 + 规则注册表 + 铲子台账 | 中；沉淀靠按需复盘，默认不自动蒸馏 |

另外两条常被业界当成「检索面」而非纯记忆：

| 面 | fawai | 业界编码 Agent |
|:---|:---|:---|
| **仓证据检索** | `fs_grep` / 轻量 `code_index` | 常驻符号 + 混合语义搜 + LSP |
| **工具/台账检索** | `shovel_search` / 能力清单 | MCP/Skills 描述 + 台账；常更宽的内置工具 |

**总判：** 存储形态已有雏形（尤其 lore 可写 + 缓冲审），**弱在检索路由、分层取用、冲突/时效，以及仓证据面**——不是「完全没记忆」。

## 3. 业界好思路（可抄架构，不必抄产品名）

### 3.1 MemGPT / Letta：把上下文当 OS 内存

```text
Core memory（钉在上下文的可编辑块：人设/偏好/当前目标）
  ↕ 模型用工具分页
Recall（对话历史可搜）  +  Archival（外存：向量/库/图）
```

要点：

1. **钉住的块**（core）≠ 整库灌进 prompt；块可由 Agent **显式改写**。  
2. **主动检索**：模型决定何时 `search_recall` / `search_archival`，而不是每轮只靠被动关键词注入。  
3. 上下文满了：**驱逐 → 摘要 → 外存**，不是静默丢掉。

对 fawai：接近「把 lore 拆成少数常驻 block + 大库工具检索」；与现有 `lore_search` / 规划注入可衔接。

### 3.2 混合检索（Hybrid），别只押向量

成熟做法几乎都是：

| 通道 | 擅长 |
|:---|:---|
| **词法**（BM25 / FTS5 / `rg`） | 标识符、报错原文、专有名词 |
| **向量** | 同义改写、「上次那种偏好」 |
| **结构**（符号/LSP/图） | 谁调用谁、实体关系、「三月时什么为真」 |
| **元数据过滤** | 用户/项目/启用态/时间窗/来源 |

排名信号常见：**相关度 × 新近度 × 作用域 × 置信度**；再 Rerank（可选小模型）。

对 fawai：lore 先上 **FTS5 + 笔记向量（已有）统一打分**；仓侧另开 **混合 code_search**（与上一份速度分析 C3 同族）。

### 3.3 写路径与生命周期（比「多一个向量库」更重要）

生产向清单（公开架构共识）：

1. **晋升**：何时从对话 → 缓冲 → 语义事实（fawai 已有 P0/P1 + 缓冲，方向对）。  
2. **冲突**：覆盖 / 追加 / **带时效的 supersede**（「昨天改了偏好」必须废旧）。  
3. **作用域**：用户 / 项目 / 会话 / 全局；禁串味。  
4. **遗忘**：一处 `forget` 同步清 KV、向量、日志引用。  
5. **溯源**：注入条目带来源任务/消息，可审计。  
6. **评估**：有无记忆的任务成功率；误召回；撤销/覆盖是否生效——不只测检索 MRR。

对 fawai：启用/停用/删除已有；缺的是 **时效版本、冲突策略、跨任务情节检索、注入带 provenance**。

### 3.4 编码场特化：仓记忆 vs 用户记忆

Cursor 类产品体感强，常靠两套：

| 套 | 内容 |
|:---|:---|
| **Codebase memory** | 后台索引：符号 + 分块嵌入；Agent 工具一次语义定位 |
| **User/project memory** | 短偏好/约定（类似 core blocks 或 Memories） |

fawai 操作分身还多一层：**桌面/路径/账号类语义事实**（适合 KV）与 **可执行铲/Skill（程序记忆）**——业界 IDE Agent 往往不需要前台租约，但记忆分层仍适用。

### 3.5 GraphRAG / 知识图（可选，后置）

关系问句（「A 依赖 B」「谁拥有该服务」）用图或三元组更稳。  
个人分身场：**先 hybrid + core blocks**；图适合实体多、关系密之后再上，避免首期过重。

### 3.6 程序记忆闭环

业界：`AGENTS.md` / Skills / 规则由人写 + 反馈环偶发自写。  
fawai：Skill + 铲子已有；**默认不自动蒸馏**（议题已定）——与「质量门优先」一致。提检索质量时，可加强 **按需复盘 → 可检索条目** 的召回，而不是重开全自动棘轮。

## 4. 欠缺对照（相对上述思路）

| # | 欠缺 | 现状 | 业界锚点 |
|:---|:---|:---|:---|
| M1 | **无明确 core memory 块** | 每轮用 goal 关键词扫 lore 摘要塞进 prompt | Letta memory blocks |
| M2 | **检索以被动注入为主** | 模型少「先搜记忆再规划」的硬习惯；`lore_search` 有但非默认分页 | MemGPT 工具分页 |
| M3 | **语义检索弱** | KV/笔记子串；向量仅笔记且与词法分通道硬拼分 | Hybrid + 统一 rerank |
| M4 | **情节记忆不可搜** | 跨任务「上次怎么做的」难主动召回 | Recall store |
| M5 | **无 supersede / 时效** | 停用/删除有；「新事实废旧事实」策略弱 | 有效窗口 / 版本链 |
| M6 | **仓证据面弱** | 无混合语义仓搜 | Codebase index |
| M7 | **注入缺 provenance** | 摘要行难回溯哪次任务写入 | 每条带来源 id |
| M8 | **程序记忆召回偏软** | Skill 注入摘要；与 goal 匹配粗 | 按 when_to_use 检索 + 工具强制先 search |

## 5. 对 fawai 可落地的思路优先级（未放行）

下列若立项，编号为**实施先后**（后项仍属范围）；可砍项单独标。

### 5.1 必要（按序）

| 序 | 方向 | 解决 |
|:---|:---|:---|
| P0 | **Hybrid lore**：SQLite FTS5（KV+笔记）∪ 现有笔记向量；统一打分（相关+新近+启用） | M3 |
| P0 | **规划前记忆路由**：短目标 → 先 `retrieve`；未命中不灌「随机 KV 键」凑数；命中带来源 | M2、M7 |
| P1 | **Core blocks（窄）**：如 `user_profile` / `work_roots` / `prefs` 钉进工作记忆；改用 `lore_set` 或专用工具 | M1 |
| P1 | **任务/复盘情节索引**：终态+摘要+关键路径可搜；`recall_search` 工具 | M4 |
| P2 | **仓 `code_search` 混合检索** | M6（与速度分析同轨） |
| P2 | **事实 supersede**：同 key 新值写 `valid_from`，旧值停用或标 superseded | M5 |
| P3 | Skill/`when_to_use` 与 lore 同一套 hybrid 检索入口 | M8 |

### 5.2 可选（可砍）

| 方向 | 说明 |
|:---|:---|
| 小模型 Rerank | 召回 20 → 精排 5 |
| 知识图 | 实体关系密后再上 |
| Agent 自主改 core block（强 MemGPT） | 先人审/工具写；全自动改人设风险高 |
| 默认打开工具观察 soft | 降工作记忆噪声；与「全文回灌」产品选择冲突 |

### 5.3 明确不建议

- 只加一个大向量库、不改写路径与冲突策略（「假记忆」）。  
- 每任务自动蒸馏污染语义库（与已否决棘轮冲突）。  
- 把整仓 lore 每轮灌进 prompt（烧 token，且挤掉工作记忆）。  
- 用更长提示「请你记住」代替可检索外存。

---

## 6. 一句话结论

**业界好思路的核心不是「再接一个 embedding API」，而是：工作记忆钉住少量块 + 情节/语义外存可主动搜 + 词法∪向量∪结构混合检索 + 写入带晋升/覆盖/遗忘。**  
fawai 已有可写 lore/Skill 与缓冲审，短板在 **Hybrid 检索、core 块、跨任务 recall、仓语义面与事实时效**；优先补 lore hybrid 与记忆路由，再叠情节索引与 `code_search`。
