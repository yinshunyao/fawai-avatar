# lore_search / lore_get：为何体感「查询意义不大」

对照对象：fawai-avatar 的 `lore_search`、`lore_get` 相对规划侧 **【个人知识库】** 被动注入，以及 `fts_search` / `name_index_search` / `fs_grep`。  
目的：解释「工具在、但用了像没用不」——钉清是引擎差、还是**产品分工把这两工具架空了**；**不等于**功能放行。

关联真源：

| 类型 | 路径 |
|:---|:---|
| 个人知识库 | [功能/个人知识库/说明.md](../功能/个人知识库/说明.md)；`fawai_lore/retrieve.py`；`lore.py` |
| 规划注入 | `brain/planner.py`（`lore_prompt_block`）；提示词「先看摘要，不足再用工具」 |
| 相邻分析 | [记忆与检索业界思路对照.md](./记忆与检索业界思路对照.md)（文内 M2）；[全文索引与Everything对照.md](./全文索引与Everything对照.md) |

**已核：** `lore_prompt_block(goal)` 与 `lore_search` 同走 `retrieve()`；注入摘要对 KV 已是 `key = value`；`lore_search` 命中带 `raw` 全文；无命中时注入会塞「部分 KV 键」；提示词明确「不足再用」而非「先搜」。  
**未核：** 现网任务里 `lore_*` 实际调用率与命中后改写规划的比例（需按 task 轨迹统计）。

---

## 1. 一句话

**不是 FTS 完全废，而是：规划每轮已经用同一套 `retrieve(goal)` 把结果塞进提示；`lore_search` 多半是重复劳动，`lore_get` 对 KV 几乎无增量，对长笔记才有用却很少被需要。**  
再叠「日常任务真正缺的是仓/可读区定位」——体感就会变成「这两个查询工具意义不大」。

```text
每轮规划
  goal ──► retrieve() ──► 【个人知识库】摘要进 system prompt
                ▲
                │ 同一套引擎
  lore_search(query≈goal) ──► 再跑一遍 retrieve() ──► 观察里多一坨相似 hits

  lore_get(key) ──► 多数时候 key/value 已在摘要或 search.raw 里
```

---

## 2. 机制层：为何「查了像白查」

### 2.1 与被动注入同构（主因）

| 面 | 行为 |
|:---|:---|
| 注入 | `lore_prompt_block(goal)` → `retrieve_prompt_block(..., query=goal)` |
| 工具 | `lore_search` → 同一 `retrieve(store, query)` |
| 提示词纪律 | 「可先看上方【个人知识库】摘要；**不足再用** lore_search / lore_get」 |

后果：

1. 注入已命中 → 再 `lore_search` 得到几乎同批 hits，**不改变决策**。  
2. 注入未命中 → 同 query 再搜通常仍空；工具**治不好**「goal 当查询词太长 / 词不对」。  
3. 模型被教成「默认不先搜」→ 工具调用率低；真调用时又常与注入重复 → **ROI 看起来接近 0**。

这与记忆对照里的 **M2（检索以被动注入为主）** 是同一根因，只是落到工具名上更具体。

### 2.2 `lore_get` 增量极窄

| 已有信息 | `lore_get` 还多给什么 |
|:---|:---|
| 注入 / search 的 KV 摘要 `key = value` | 几乎没有（再读一遍同条） |
| `lore_search` 的 `raw`（已含 `to_dict()`） | 对 KV/笔记字段再包一层，无新事实 |
| 仅摘要里笔记 120 字预览、且未带回 `raw` 的旧路径 | 全文 body——**唯一常有意义的增量** |

因此：库以 **短 KV（路径、账号落点）** 为主时，`lore_get` 产品意义天然弱；只有「长笔记要读全文」才值得第二跳，而当前任务形态很少走到那里。

### 2.3 无命中时的「假相关」注入伤害信任

`retrieve_prompt_block` 在 hits 为空时会列出最多约 12 个 KV 键当凑数，标题写「无精确命中；部分 KV 键」。

| 对规划 | 对工具观感 |
|:---|:---|
| 提示里已有一串未必相关的 key=value | 模型以为「记忆已经给过了」 |
| 再 `lore_search` 仍空或仍噪声 | 更觉得检索工具没用 |
| 真正相关事实若关键词没撞上 | 既不在注入里，工具也不会 magically 出来 |

记忆对照 P0 已写：「未命中不灌随机 KV」——正是在堵这条。

### 2.4 查询面错位：用户要的「搜」≠ lore 库

| 意图 | 该走的面 | 走 lore_* 时 |
|:---|:---|:---|
| 文件名 / 路径 | `name_index_search` / `fs_glob` | 库里没有则空 |
| 可读区正文 | `fts_search` / `fs_grep` | 扫错库 |
| 仓内代码 | `fs_grep` / `code_*` | 同上 |
| 个人事实（数据集根、口令落点文档名） | lore | 才对口 |

分身日常大量是前三类。`lore_search` 名字像「搜知识」，范围却是 **lore 存储**；期望错位会直接判工具「没意义」。

### 2.5 激励与路由偏软

- 能力说明只写「按关键词检索」，**没有**硬闸「查账号/路径必须先 lore_search」。  
- 编码主路径提示堆在 `fs_grep` / `fs_glob`；lore 只有短句「不足再用」。  
- 无「规划前强制记忆路由、未命中禁止乱灌」——工具停留在可选旁路。

## 3. 不是主因（避免误诊）

| 说法 | 判断 |
|:---|:---|
| 「完全没建 FTS」 | 已有 `{lore}/fts.sqlite`，retrieve 优先 FTS5；问题不在「有没有引擎」 |
| 「lore_get / search 实现坏了」 | 冒烟与 Web 工具测试可用；坏的是**相对注入的增量价值** |
| 「只要换更大向量库就好」 | 向量目前主要服务笔记；KV 短事实更吃词法；不解决同构重复 |

---

## 4. 改进方向（未放行；均为可选项，可砍）

下列不是实施优先级清单里的「全要做」；**砍掉不影响**「工具可自测」的现网验收。若立项，建议按「先消冗余、再补缺口」。

| 方向 | 解决什么 |
|:---|:---|
| **消冗余**：注入已带完整 KV value 时，提示写明「勿再 lore_get 同 key」；search 命中默认只回 summary+id，长笔记再 get | `lore_get` 虚工具感 |
| **记忆路由**：规划前对短意图词跑 retrieve；命中钉进 core 块；**未命中不塞随机键**；必要时系统代调一次 search 再规划 | 同构重复 + 假相关 |
| **改写查询**：禁止把整段 goal 当 FTS query；抽 1～3 个实体词再搜 | 空结果假阴性 |
| **场景硬提示**：仅「账号/配置落点/数据集根」类目标强制先 lore；编码改文件默认不展示 lore 检索为优先工具 | 错面误用 |
| **合并工具**：`lore_lookup(query, get_id?)` 一次返回命中+可选全文，去掉无增量的两跳 | 心智负担 |
| **情节/仓面另开**：跨任务 recall、`fts_search` 加强——别指望 lore_* 扛所有「搜」 | 期望复位 |

与记忆对照 **P0 Hybrid + 规划前记忆路由**、全文索引文「索引治不好无路由」一致；本文只把矛头对准 **为何这两个动作名显得多余**。

---

## 5. 结论

体感「lore_search / lore_get 查询意义不大」，主因是：

1. **与每轮被动 `retrieve(goal)` 同构**，工具难提供新信息；  
2. **`lore_get` 对短 KV 无增量**，第二跳常浪费；  
3. **真正高频的定位需求在仓/可读区**，不在 lore 库；  
4. **软提示 + 无命中灌噪声键**，既不催主动搜，又损害「记忆有用」的信任。

引擎（FTS/向量）可以继续加强，但若不改「注入 vs 工具」的分工与路由，这两工具会一直像可选重复接口。

## 6. 旧「全表子串」建库/查询能否取消？（已核）

| 层 | 是什么 | 能否取消 |
|:---|:---|:---|
| **存储** | `kv.json` + `notes/*.json`（旁路写入、启用/停用） | **不能**。FTS / 向量只是索引，真源仍是这套库 |
| **写入建库** | `lore_set` / `lore_note_upsert` / sidecar 落盘，再同步 `fts.sqlite` | **不能取消写入**；旧方式没有单独「建子串库」，只是每次全表扫 |
| **`lore_search` 旧查询** | `list_all` → 拼 blob → `token in blob`（retrieve 里 `source=keyword` 回落） | **可以取消作主路径**；FTS5 已是默认真源，且缺库会自动建 |
| **`lore_get`** | 按 key / note id **精确读一条** | **不能取消**。不是「搜」；FTS 替不了点名读取 |
| **向量** | 笔记语义近邻 | 与子串无关；按开关保留 |

```text
保留：KV/笔记落盘 ──► 写时同步 FTS ──► lore_search = FTS（±向量）
                                            lore_get  = 精确 get
可砍：retrieve 里「FTS 未用则全表子串」回落（或仅测试/无 FTS5 构建时保留）
```

**建议：** 取消的是**全表子串检索回落**，不是取消 `lore_search` / `lore_get` 工具本身，也不是取消知识库存盘。  
若砍回落：须保证 FTS 开关开且 `ensure_lore_fts` 成功；无 FTS5 的环境应显式失败或空结果，而不是静默退回扫表。

## 7. 更深一层：不是「索引坏了」，是「当知识库的东西不对」（用户澄清）

用户判断：`kv.json` / `notes/` 落盘与旁路写入后，**按 key/value 查出来意义不大**——感觉以前「建知识库」的方式就不对。

要把三件事拆开，否则会误砍真源或误留废品：

| 层 | 以前实际在做什么 | 为何体感没意义 |
|:---|:---|:---|
| **A. 索引算法** | 全表子串；现已可 FTS | 换引擎只让「错库」搜得更快，**不自动变有用** |
| **B. 入库内容** | 旁路抽 `dataset.xxx.root` 一类英文点分 key + 短 value；P1 偏好进缓冲/直写 | 大量条目是**地址簿碎片**，不是「可回答问题的知识」；查回来仍是 `key=value`，对规划像噪声 |
| **C. 查询产品面** | `lore_search` / 注入都以「关键词撞 KV/笔记」当主记忆搜 | 用户日常要的是**工作区文件名/正文**；lore 面扛了「搜知识」的名，装的却是短事实 |

```text
以前隐含模型：
  对话里抽出 key/value ──► 落盘 ──► 再搜 key/value ＝「有了知识库」

更贴场的模型：
  工作区正文/文件名索引 ＝ 主知识面（已在 memory_index）
  短 KV                 ＝ 少量「钉住的地址/偏好」（core），靠精确 get，不靠搜戏
  长笔记 / 情节         ＝ 真要「搜着回忆」的个人知识（若要留 lore，应偏笔记与复盘，而非堆 key）
```

### 7.1 哪些「以前的建立方式」可以判为意义不大

| 做法 | 判定 |
|:---|:---|
| 把旁路抽到的大量短 KV 当「知识库主资产」并每轮检索/注入 | **意义不大**（与用户体感一致） |
| 用子串/FTS 去「搜」这些短 KV 当主召回 | **产品面错位**；精确 `lore_get(key)` 才对口 |
| 未命中时灌一串无关 `key=value` | **有害**（假相关） |
| `kv.json`/`notes/` 作为可审计落盘容器本身 | **容器可留**；问题在**写什么、怎么暴露查询** |

### 7.2 建议方向（未放行；下列为必要方向 vs 可选项）

**必要（若接受「短 KV 不是主知识」）：**

1. **主知识面改口**：规划与工具默认「搜知识」→ `name_index_search` / `fts_search`（工作区）；lore 不再冒充万能搜。  
2. **短 KV 降权**：注入只留极窄 core（工作区根、少数已确认路径）；禁止未命中灌键；旁路 P1 默认进缓冲、少直写。  
3. **砍子串回落**：检索真源 FTS；无索引则空，不扫表凑命中。

**可选（可砍）：**

- 弱化或停用「从闲聊自动抽大量 KV」的 LLM propose 默认开。  
- `lore_search` 改为只搜 **笔记/情节**，KV 不进 search（只进 get / core）。  
- 存量无用 KV 批量停用或归档（人工确认后再做）。

**禁止误解：** 不等于立刻删掉 `kv.json` 与旁路；先改**写什么、查哪张面**，再谈清库。

## 8. 落地状态（已切换引擎）

| 项 | 状态 |
|:---|:---|
| `lore_search` / HTTP `/api/lore/search` | → `knowledge_search`（content_fts ∪ name_index ∪ 笔记 FTS/向量） |
| `lore_get` / HTTP `/api/lore/get` | → `knowledge_get`（笔记 / 路径 / 索引；**不以 KV key 为主**） |

| 旁路 / `kv.json` 落盘 | **旁路默认关**（`FAWAI_LORE_SIDECAR=0`）；存量短 KV/缓冲可 `purge-short-kv` 清空；已退出主搜产品面 |
