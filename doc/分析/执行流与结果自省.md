# 执行流与结果自省

## 现状

步骤分类把一段动作收成 `act_serial` / `act_parallel`，段中不进规划。衔接只靠两件事：工具 `ok`，以及可选的 `Action.expect`（`contains` / `not_contains` / `contains_any`）。见 [动作段预期闸](../功能/动作段预期闸/说明.md)、[步骤分类与执行流](../功能/步骤分类与执行流/说明.md)。

现有工具的 `expect` 已支持精确子串（`contains`）和模糊多选（`contains_any`）。规划提示改为多步执行流倾向带上，缺省不拒。新建脚本约定打 `OK` / `FAIL:` 行；已有铲不回改。段末观察反省仍是另一层，不能代替单步机读闸。

## 判断

多步执行流**应当约束调用侧具备结果自省**，但自省是**机读信号**，不是在脚本里再跑一轮模型。

| 层 | 自省放哪 | 要求 |
|:---|:---|:---|
| 内置只读（`fs_read` / `fs_grep` / `fs_glob`） | 工具 `ok` 即可 | 下一步不依赖某个具体字串时，不必强行 `expect` |
| `act_serial` 里后步吃前步结果 | 调用上的 `expect` | 规划倾向写上：精确 `contains`，模糊 `contains_any`；不满足则停段。缺省不拒 |
| 生成脚本 / `py_run` / `shell` / 铲子调用 | 脚本自己打出短结论 + 非零退出 | stdout 有稳定一行（如 `OK` / `FAIL:…`），调用侧用 expect 或退出码接上；禁止只靠「进程没崩」当业务成功 |
| `act_parallel` | 各动作各自 `ok` | 无相互衔接，段末再统一观察；不为了并行去写跨动作 expect |
| 段末 | 工具结果观察 + 观察反省 | 整段看完再分析；不把段末 LLM 塞进每个脚本 |

## 不做

- 不在生成代码里调用规划/反省模型。
- 不要求每一次 `fs_grep` 都带 expect。
- 不把「脚本打印了很长日志」当成已自省。

## 与放行的关系

用户定：**不做硬闸**。规划多步执行流时倾向带精确（`contains`）或模糊（`contains_any`）预期；新建脚本在提示、能力说明、`SHOVEL.md` 与脚手架模板里写明结果行。缺 expect 不拒规划。已有铲不因缺 `OK` 行而校验失败。
