## 1. fawai 现在怎么处理任务

### 1.1 默认路径（非 Plan）

```text
用户目标 → 总管 create 工作任务 → WorkerLoop
  观察 → 执行脑 plan(下一步) → 控制执行 → 反省/重复闸 → …
  直至 success / failed / need_input
```

- **单任务稠密闭环**：每轮只规划「下一步」，靠多轮推进。
- **同任务内加速**：主脑可 `delegate` 快模型跑一段子目标，摘要回灌（仍是同一 Worker）。
- **多任务底座**：总管可并存多个工作任务；`foreground_lease` 前台串行；后台写资源清单仲裁。

### 1.2 Plan 模式路径（MVP）

```text
用户目标
  → 编排脑 decide_complexity（无人审）
  → enter=false：走默认单 Worker
  → enter=true：编排脑出任务图 → 父计划(orchestrator，不跑步)
       → 规则按就绪集 create 监管脑子任务
       → 各监管脑驱执行脑自闭环
       → 节点成功：规则衔接下游（零编排 LLM）
       → 追加对话：编排脑先分析再下发
```

三层大脑分工：**编排脑稀疏**（判定/出图/租约/追加重排）→ **监管脑稠密完成节点** → **执行脑步级**。

**会话 UX（已落地）**：监管脑子任务**不进侧栏**；进度/终态归并到父计划同一会话；父线程**右上角浮层任务图**（默认折叠，点击展开）按 `depends_on` 分层并实时刷节点状态（对齐 Cursor「单会话内看清计划图」的观感，不是再拆成独立对话；主会话气泡仍占主视觉）。

### 1.3 产品场

面向 **PC/手机操作分身**（文件/shell/GUI/浏览器等），不只是仓内改码；租约与前台互斥是一等约束。

## 2. Cursor 常见任务处理（对照口径）

| 形态 | 特征（公开/常用） |
|:---|:---|
| **Agent 默认** | 单会话代理 + 工具循环；中途可用 Todo 跟踪；上下文强绑 IDE（打开文件、diff、终端、索引） |
| **Plan** | 先产出可编辑计划/步骤，再执行；常保留人审或显式「按计划做」；计划与执行多在**同一代理上下文**或紧耦合续跑 |
| **Task / 子代理** | 可并行派探索类子代理；云端子代理可带独立 worktree；结果回灌父代理 |
| **主场** | 代码仓 + 编辑器工作流；桌面任意 App 操控非主叙事 |

## 3. 模式对照（一张表）

| 维度 | fawai（含 Plan MVP） | Cursor |
|:---|:---|:---|
| **默认粒度** | 单 Worker 逐步；复杂则出图拆 Worker | 单 Agent 逐步；复杂可进 Plan / 拆子代理 |
| **谁判复杂** | **编排脑自动判**，无人勾选 | 用户开 Plan / 模型建议；产品常保留人控 |
| **出图后** | **自动调度**监管脑 | 常可审改计划后再跑 |
| **执行隔离** | 多工作任务 + 独立轨迹；父计划不吃步噪声 | 子代理隔离较好；同会话 Plan 仍易共享一大上下文 |
| **并行** | 图上无依赖可并；**前台键鼠硬串行**；写资源租约 | 子代理可并（尤其只读探索）；无「整台前台锁」语义 |
| **中层角色** | 显式**监管脑**完成节点 | 父代理 + 子代理；较少「节点监管」产品名 |
| **衔接** | 成功路径**规则**走依赖边 | 多靠父代理再规划/汇总 |
| **追加对话** | Plan 下**先编排脑**再下发 | 同会话追加进当前 Agent；Plan 修订靠人/模型 |
| **主战场** | 操作分身（GUI+文件+shell） | IDE 编码与仓内工具 |

## 4. fawai Plan 模式：优点

1. **稀疏编排防过载**：步级状态不进编排脑；成功衔接零编排 LLM——适合长任务、多节点并发。
2. **物理世界约束一等公民**：前台 lease + 写资源清单，是 Cursor 代码主场不必面对的硬问题；Plan 图可挂 `modality_hint`。
3. **上下文隔离**：每节点独立 Worker/监管授权，避免「整本大计划塞进一个逐步脑」。
4. **自动进模 + 自动开跑**：编排脑判定、出图即调度，自动化托管友好（少一次人机闸）。
5. **与总管任务线对齐**：暂停/取消/续跑/列表已有底座，Plan 是挂图调度，不是另起聊天脚本。

## 5. fawai Plan 模式：缺点（含 MVP 缺口）

1. **出图质量不稳**：LLM/启发式拆句易假依赖或漏依赖；远不如 Cursor Plan 在「可编辑、可回看」上的成熟度。
2. **人机协作品弱**：无人审是刻意选择，但缺「看图改边再跑」；出错成本由自动跑放大。
3. ~~**reorder / 租约调整未做实**~~ → **已做实**（`plan_revise` + `apply_plan_revision`：改图、cancel 过时 running、重拉就绪集；lease_adjust 调 modality）。
4. **三层调用成本**：判定 + 出图 + 每节点执行（+ 可选委派）token/延迟高于单 Agent。
5. **会话 UX**：父/子任务折叠、计划进度卡仍弱；用户难一眼看懂「图在哪一步」。
6. **编码并行隔离不及 Cursor 云子代理**：无独立 worktree/分支默认策略；多节点改同一仓仍靠租约，不是沙箱分叉。

## 6. 相对 Cursor：谁强在哪

| 场景 | 更合适 | 原因 |
|:---|:---|:---|
| 仓内多文件重构、要审计划再改 | **Cursor** | Plan 可编辑 + Diff/Lint 接地 + 子代理探仓成熟 |
| 桌面多 App / 前台互斥 / 后台并行写不同路径 | **fawai** | 租约 + 多 Worker + 操作分身工具面 |
| 全自动托管长流程、少点确认 | **fawai Plan 取向** | 编排脑自判 + 自动调度（代价是可控性） |
| 要人盯着改计划再执行 | **Cursor** | 人审 Plan 是常态能力 |
| 只读大范围探仓并行 | **Cursor Task** | 子代理/云代理产品化更完整 |
| 节点失败后局部重开、规则接下游 | **fawai 设计方向** | 依赖边 + 监管脑边界清晰（落地仍需加强改图） |

## 7. 可后续开议题的改进方向（非放行）

| 优先级 | 方向 | 备注 |
|:---|:---|:---|
| P1 | 计划卡只读进度（节点终态） | 对齐 Cursor「看得见计划」但不改「无人审开跑」 |
| P1 | ~~`reorder` 真改未决子图~~ | **已落地**（见功能「复杂任务计划模式」） |
| P1 | 出图质量评测集 | 复杂目标拆图 vs 人工金标 |
| P2（可选） | 可选「仅出图不调度」口令 | 与默认自动跑并存，服务要盯图的用户 |
| P2 | 编码节点 worktree/分支策略 | 学 Cursor 隔离，仍受租约约束 |
