# 计划会话：严格时序与节点卡拆分

| 项 | 说明 |
|:---|:---|
| 对照 | 当前 PWA 线程 DOM（`#msgs` / `#planEpochs` / `.plan-epoch` / `.plan-node-card` / `step-stream`） |
| 目的 | 说明层 1～5 修完后仍「看起来乱」的根因；对齐「整段对话按真实发送/执行时刻从上到下」的目标态 |
| 关联 | `doc/问题/追加会话贴在节点上方.md`；功能说明见 `doc/功能/复杂任务计划模式/说明.md`、`doc/功能/会话通道/说明.md` |
| 状态 | **分析备忘，未放行改代码** |

## 现状（层 5 之后）

计划任务交互尽量进 `#planEpochs`，顶层 `.plan-epoch` 与桥接 `.row` 可按 `data-ts` 插队。历史回放也会先灌轨再回放信封。

仍保留的结构约束：

1. **一轮计划 = 一个 `.plan-epoch` 块**（内含 `rail` + 多张节点卡 + `tail`）。
2. **一个节点 = 一张 `.plan-node-card`**，体内一条 `step-stream` **连续堆叠**该节点全部步骤/吸收/取消/节点完成。
3. 顶层排序只比较 **epoch / 独立 `.row` 的 `data-ts`**；卡内事件**不再参与**与卡外气泡的横向比时。

因此：只要对话、回执、续跑步骤有一部分挂在卡外（或另一宿主），而另一部分灌进卡内，视觉顺序就由「整块卡」决定，而不是由每条事件自己的时刻决定。

## 截图在说明什么

自上而下可见：

1. 节点步骤流：`已吸收 1 条用户追加` → `#82`…`#85` → `已取消`（**06:57**）→ `节点完成 … cancelled`（**06:57**）
2. 用户泡：找不到密码（**21:56**）
3. 用户泡：权重不是最新（**22:05**）
4. 系统：`编排脑已处理追加 (dispatch_note)…`（**22:05**）
5. 用户泡：`继续执行…`（排在「已处理追加」**之后**）

两处硬伤（与钟点是否跨日无关，语义上已乱）：

| 现象 | 按交互应有的顺序 | 现 UI |
|:---|:---|:---|
| 吸收 vs 被吸收的话 | 先出现用户追加（如「继续执行」等），再「已吸收 / 已处理追加」，再后续步骤 | 「已吸收」在步骤流顶部；对应用户泡在整块步骤/取消**下面** |
| 追加回执 vs 用户令 | 先用户「继续执行」，再「编排脑已处理追加」 | 回执在上，令在下 |

06:57 与 21:56 并排时，若分属「次日清晨取消」与「前一晚追问」，Unix 时序应晚间在前、清晨在后；当前却因取消写在**早已挂上的整块节点卡内**，卡外晚间泡只能插在整卡之后，于是清晨取消压在晚间对话之上。即便同日，**「吸收」仍不得出现在被吸收内容之前**。

## 根因（相对层 5）

层 5 解决的是「脊柱 `#msgs` 整块压在节点轨前」和「epoch 用 `Date.now()` 导致续跑插到轨前」。  
**没有**改变「节点卡 / 步骤流是不可拆的时间胶囊」：

```text
#planEpochs
├── .plan-epoch[data-ts=节点轨起点]          ← 整块只占一个时序槽
│     └── .plan-node-card
│           └── step-stream
│                 ├── 已吸收…                 （实际可能很晚）
│                 ├── #82 … #85
│                 ├── 取消 06:57
│                 └── 节点完成 06:57
├── .row.user 21:56                          ← 只能和 epoch 比 ts，进不了卡中段
├── .row.user 22:05
├── .row 编排脑已处理追加 22:05
└── .row.user 继续执行                        ← 与回执同秒/锚点错时仍可能颠倒
```

卡外消息按 `ts` 与 **epoch 起点**比较：起点偏早 → 晚间对话全部落到「含清晨取消的整卡」下面；卡内后发生的步骤不会把卡「推开」给中间对话留位。

次要：部分用户泡未稳定进节点流（无 `plan_node_id` / remount 未追上），与「已吸收」分属卡内/卡外两条车道。`insertMsgRowAfter` / `inbound_id` 仍可能让「继续执行」与 `dispatch_note` 回执颠倒。

## 目标态（用户约束）

- 整段对话 **严格按真实时刻从上到下**（早 → 晚）。
- **允许**执行节点卡拆分：中间可插入对话、回执、追加。
- **允许**子步骤流拆分：步骤与步骤之间可插入对话等。
- 多段交互按实际发送/执行切开展示，而不是为保「一张卡视觉完整」牺牲时序。
- **重试 / 从某步恢复 / 整节点重跑**：须**保留全部历史卡片与全部历史子步骤**（含失败、取消、被截断前的旧跑），新跑是时间线上的**追加段**，不是覆盖；新旧之间若有用户对话，按真实时刻插在中间。

## 重试与恢复：现状 vs 目标（补强）

产品已支持（见功能说明）：失败节点重试、整图重规划、步骤「从此恢复」、挖步等。会话轨侧相关机制：

| 机制 | 意图 | 与「保留全部历史 + 严格时序」的缝 |
|:---|:---|:---|
| `openPlanEpochForRetry` | 封存当前轮再开新轮，避免 Failed 被新节点顶乱 | 直播路径大致「旧轮封存、新轮新卡」；**历史回放**常按**终态图** `syncPlanNodeRail`，易收成「每 `node_id` 一张活卡」，旧跑步骤依赖信封能否完整重建 |
| 同节点换 `run_id` / `plan_child_task_id` → `run-switch` 开新轮 | 禁止多 Worker 步骤叠进同一卡 | 正确方向；若软续跑/吸收未换 run，仍往**同一** `step-stream` 尾部堆，与卡外对话无法交织 |
| `epoch.cards` 以 `node_id` 为键 | 一轮内一节点一卡 | **同轮内**第二次跑同一 `n1`（或恢复后新序列）若未强制新轮，会复用同一卡，旧步骤与新步骤粘在一条流里，或被 upsert 成「像覆盖」 |
| 「从此恢复」截断监管脑上下文再拉 Worker | 业务上从第 N 步重跑 | UI 若仍写回原 panel，易表现为步骤号重来、旧 #k 后直接接新 #k，**看不清这是第二次执行**；目标应是：旧段完整保留（可标 cancelled/superseded）→ 中间若有用户操作/对话 → **新段**再出步骤 |
| 封存轮 `sortPlanNodeRail` 不重排 | 保护封存顺序 | 封存的是整轮块；轮外对话仍只与 epoch `data-ts` 比，插不进轮内两张卡之间的「真实间隙」 |

目标时间线示意（同节点重跑两次，中间夹对话）：

```text
… 用户追问 / 点「重试本节点」/「从此恢复」 …
n1 · 第 1 次执行（完整历史卡 + #0…#k，含失败或取消现场）
… 中间其它对话 / 回执 …
n1 · 第 2 次执行（另一张历史卡或明确新段 + 新步骤序列）
… 更晚的对话 …
```

禁止的目标态误解：

- 只保留「当前这次」节点卡，旧跑步骤被清掉或只留在折叠摘要里不可按序 Scrub
- 同 `node_id` 永远只有一张卡，重跑步骤追加在同一 stream 底部且中间对话被挤到整卡外
- 用终态图回放时把多轮执行折成一张卡上的最终状态

身份键建议（实现时再定，此处只钉需求）：时间线上的「一次节点执行」至少区分 `node_id` + `run_id`（或 `plan_child_task_id` / epoch 段号）；步骤事件带自身 `ts` 与所属 run，重号（再次出现 `#3`）是正常的**第二次执行**，不是同一条的编辑。

## 改进方向（未实施）

下列均为**必要项的候选拆法**（实施先后待议题确认；默认是优先级不是可砍，除非另行标明可选）：

1. **时间线原子改为「事件 / 执行段」而非「整卡」**  
   用户泡、回执、progress 步、节点执行段头/收尾，按 `ts` 成为同一宿主上的兄弟；同 `node_id` 可有多段（对话切开，或重试/恢复切开）。

2. **插入中段对话或重跑时封口并开新段**  
   对话落入已有执行段时间窗内 → 封段 → 挂对话 → 同节点新段。重试 / 从此恢复 / 换 run → **必须**新段（或新卡实例），旧段只读保留。

3. **历史回放按全局 `ts` + run 归并**  
   信封与节点事件先排成一条时间河再挂 DOM；禁止「终态图先灌成每节点一卡」把多跑折成一跑。

4. **追加因果链**  
   用户令 → 受理/路由/`dispatch_note` →「已吸收」→ 后续步；禁止回执与令颠倒。

5. **（与重试相关）执行段元数据**  
   段头可见「第 N 次 / 自步骤 k 恢复 / run 短 id」，避免用户把重复的 `#0…` 当成 UI 打乱；可选折叠旧段，但折叠不得删除时序位置。
