# 全文索引与 Everything 对照

对照对象：fawai-avatar 仓/知识检索，相对 Voidtools **Everything**（俗称「Find Everything」）式预索引，以及常规 **全文检索（Full-Text Search，FTS）** 倒排索引。  
目的：回应「搜索弱，能否先建索引」——分清索引类型、怎么建、对 fawai 哪一层有用；**不等于**功能放行。

关联真源：

| 类型 | 路径 |
|:---|:---|
| 仓检索 / `fs_grep` | [功能/编码闭环/说明.md](../功能/编码闭环/说明.md)；`workspace/fs.py` |
| 代码索引（符号，非全文） | [功能/代码索引/说明.md](../功能/代码索引/说明.md)；`workspace/code_index.py` |
| 个人知识库 | [功能/个人知识库/说明.md](../功能/个人知识库/说明.md) |
| 相邻分析 | [工具与文本检索速度对照.md](./工具与文本检索速度对照.md)；[记忆与检索业界思路对照.md](./记忆与检索业界思路对照.md)；[数据盘索引按业务划分.md](./数据盘索引按业务划分.md) |

**已核：** `fs_grep` 默认仍为查询时 `rg`/walk；`code_index` 为符号表 JSONL。  
**引擎（已落地）：** `lore_search` = 工作区正文 FTS ∪ 文件名索引 ∪ 笔记 FTS/向量（`knowledge_search`）；笔记库 `{lore}/fts.sqlite`；正文/文件名默认扫**工作区**（`work_root`），库在 `data/memory_index/`。**不搜旁路短 KV。** 缺库首次查询可自动建；配置在 `memory_settings.sqlite`；`/` 与用户主目录拒扫。  
**未核：** Everything 商业版内容索引实现细节；Zoekt 部署成本在本机分身场的实测。

## 1. 先对齐：Everything ≠ 全文索引

| | Everything（典型用法） | 常规全文索引 |
|:---|:---|:---|
| **主要索引什么** | 路径、文件名、大小、时间等元数据 | 文件/文档**正文**里的词与位置 |
| **为何极快** | Windows 上读 NTFS USN Journal，几乎实时跟变更；查询走内存/磁盘上的路径字典，不打开文件内容 | 查询走倒排表，不必再扫原文 |
| **回答的问题** | 「哪个文件叫 / 路径含 xxx」 | 「哪段正文含这个词 / 短语」 |
| **内容搜** | 可选扩展；默认不是正文 FTS | 正是目标 |

对 fawai：用户骂「搜得弱」，多数是 **正文定位弱**（该改哪段代码、配置落在哪句），不是「文件名找不到」。  
Everything 思路对 **`fs_glob` / 按名找路径** 有启发；对 **`fs_grep` 正文** 要对标的是 FTS / Zoekt / 混合检索，不是纯路径索引。

### 1.1 文件名规范时：Everything 式还有没有效率与意义？

**有，而且规范命名会抬高「意义」，不一定再抬「绝对速度差」。**

| 维度 | 文件名乱 / 无语义 | 文件名规范（版本号、场景、实验 id、职责词写进路径） |
|:---|:---|:---|
| **查询算力** | 路径索引仍极轻：只碰路径字典，不读正文 | **同样轻**——效率来自「不打开文件」，与命名好坏无关 |
| **命中质量** | 按名找常空或噪声大，仍要靠正文 FTS/`rg` | **显著升高**：`cub`、`keep-snap-flip`、`train_ba`、`结论.md` 一类词直接钉文件 |
| **对 Agent 的意义** | 弱：模型猜不出文件叫什么，路径索引帮不上忙 | **强**：规划可先 `按名/路径` 再决定要不要 `grep`；少一轮盲扫正文 |
| **相对冷 walk 的 ROI** | 宽根大树时仍省；窄小树可忽略 | 宽根时仍省；小树里绝对增益不大，但 **产品动作仍成立**（「先名后文」路由） |

机制上：

```text
效率：路径索引成本 ≈ O(路径条数的字典/前缀查)，与正文体积无关 → 永远比开文件扫内容便宜。
意义：命名把「意图」写进路径 → Everything 类查询从「找文件名玩具」变成「第一召回通道」。
```

因此：**规范命名不是「就不需要路径索引」的理由，反而是「路径索引更值得做」的理由**——效率天花板本来就很高；规范命名把命中率拉上来，产品意义才兑现。  
反过来：命名再规范，也**替代不了**正文 FTS（「这句话在哪个文件第几行」仍要词法/正则）；两条线互补。

对 fawai 的取舍（仍未放行）：实验树、数据集别名、配置快照等目录若命名纪律好，**线 A（路径元数据）相对 P2 的性价比上调**——尤其在宽 `READ_ROOTS` 仍要按名跳转时；若根已收窄且文件少，可继续靠 `fs_glob`/`rg --files`，把工程优先留给 lore FTS / 仓内正文索引。

## 2. 正常全文索引怎么建（机制）

核心数据结构是 **倒排索引（inverted index）**：词 → 出现在哪些文档（及可选位置）。

```text
入库流水（离线或增量）：

  文档集合（文件 / 笔记 / 分块）
       │
       ▼
  ① 采集：读路径、正文、mtime/size；跳过二进制与 ignore
       │
       ▼
  ② 分块（可选）：按行/段落/函数窗切成 chunk，带 path:line 溯源
       │
       ▼
  ③ 分词 / 规范化：
       · 英文：小写、去标点、可选 stemming
       · 标识符：常另切 camelCase / snake_case（code search 关键）
       · 中文：词典切分或 n-gram（否则「全文」对中文几乎废）
       │
       ▼
  ④ 写倒排：term → [(doc_id, tf, [pos…]), …]
       + 正排/元数据：doc_id → path, mtime, 长度, 可选原文指针
       │
       ▼
  ⑤ 查询：解析 query → 查 posting list → 交/并/短语邻近 → 打分（TF-IDF / BM25）→ 返回命中

增量：文件 mtime/size 变则删旧 posting、重切该文档；删文件则从正排与倒排抹掉。
```

| 落地层 | 常见选型 | 说明 |
|:---|:---|:---|
| 嵌入式 | SQLite **FTS5** | 个人库 / lore 最合适；BM25 可选 |
| 代码仓正则向 | Zoekt、部分 IDE Instant Search | 预索引三元组，宽正则也亚秒 |
| 通用搜 | Lucene / Tantivy / Elasticsearch | 重；个人分身场通常过重 |
| 混合 | FTS ∪ 向量 ∪ 符号 | 词法钉标识符；向量钉同义；符号钉结构 |

**与「每次 `rg`」的差别：**  
`rg` = **查询时扫描**（有忽略规则，但无持久倒排）。  
FTS = **写入时付成本，查询时读表**。仓大、重复搜、多轮试错时，预索引才划算。

## 2.1 SQLite FTS5 到底能做啥（白话）

FTS5 = SQLite 自带的**全文检索虚拟表**。你仍用普通表存 KV/笔记；另建一张 `…_fts` 表，写入时把可搜字段塞进去，SQLite 在库内维护倒排。查询时：

```sql
SELECT … FROM lore_fts WHERE lore_fts MATCH 'cub AND dataset'
ORDER BY rank LIMIT 10;
```

相对现在 lore 的「`list_all` → 拼大字符串 → `token in blob` 计分」，FTS5 多出来的是这些**具体能力**：

| 能力 | 一句话 | 对 lore 的例子 |
|:---|:---|:---|
| **按词查，不扫全表** | 只碰含该词的行，条目上千也快 | `MATCH 'CUB'` 直接命中，不必加载全部笔记再 `in` |
| **多词逻辑** | `AND` / `OR` / `NOT`、短语 `"exact phrase"` | 「同时含 比昂 与 5080」；排除已停用类词 |
| **前缀** | `train*` | 打半个词也能找 `training` / `train_ba`（英文/标识符友好） |
| **排序（BM25）** | 词越稀有、越集中，分越高 | 比「命中几个子串就 +1」更像搜引擎；少把废笔记顶到前面 |
| **多列权重** | title 比 body 更重要 | 标题命中 `dataset.cub.root` 压过正文偶尔提到 CUB 的长笔记 |
| **高亮片段（可选）** | `snippet()` / `highlight()` | 注入规划时只回一两句命中上下文，不整篇灌 prompt |
| **跟业务表同库事务** | 写笔记 + 更新 FTS 一次 commit | 与现有 sqlite / JSON 演进兼容；不必另起 Elasticsearch |

**它不做什么（别期待错）：**

| 不是 | 说明 |
|:---|:---|
| 不是语义搜 | 「上次那种偏好」仍靠向量；FTS 要字面词对得上（或你自己扩同义词） |
| 不是正则 `rg` | 复杂正则、跨文件行上下文仍用 `fs_grep`；FTS 是**词袋/短语** |
| 不是 Everything | 不管整盘文件名实时索引；只管你塞进 FTS 表的那些行 |
| 中文默认较弱 | 默认按 Unicode 空格/标点切；中文常无空格 → 要 **unicode61 + 自备切词**，或 **trigram** tokenizer，否则「数据集路径」整句当一个巨词，搜「数据集」可能空 |

**和现有可选向量怎么分工：**

```text
词法 FTS5：  专有名词、路径、键名、报错原文  → 准、快、可解释
向量（已有）：同义改写、模糊回忆               → 补「词对不上」
统一打分：   两路召回合并 → 相关度 × 新近 × 启用态
```

一句话：**FTS5 = 给 lore（或任意小库）加一张「搜引擎用的词索引表」**；能做的事就是上面那张「按词查 / 多词逻辑 / 前缀 / BM25 / 列权重 / 片段」——不是魔法语义，也不是整盘 Everything。

## 2.2 「FTS5 词表上叠向量」行不行？

**结论：能做语义搜，但不要叠在 FTS5 的词表（term 字典）上；应叠在同一批文档/分块上，与 FTS5 并列，再混合打分。**

| 做法 | 向量编什么 | 能不能叫语义搜 | 评价 |
|:---|:---|:---|:---|
| **A. 文档/分块向量（正确主路径）** | 每条笔记 / chunk 的正文嵌入 | 是 | 业界 hybrid 标准；与 FTS5 共用 `doc_id`/`rowid` |
| **B. 给 FTS5 词表里的 term 做向量** | 词典里每个词一个嵌入，查询时找近邻词再 `MATCH` | 最多是**同义词扩展** | 便宜但弱：扩不出「上次那种偏好」类整句语义；噪声大 |
| **C. 只靠 FTS5 本身** | 无 | 否 | 字面词对不上就空 |

```text
正确叠法（同库并列，不是「改词表」）：

  笔记 / chunk（同一 rowid）
       ├──→ FTS5 虚拟表     （词法：MATCH + BM25）
       └──→ vec0 / 向量表   （语义：近邻 top-k）
                    │
                    ▼
            两路召回 → RRF / 加权合并 → 再乘新近 × 启用态
```

**为何不是「改 FTS5 词表」：**  
FTS5 维护的是 **term → posting list**（倒排）。向量要表达的是 **文档在语义空间的位置**。两者索引键不同；硬把词向量塞进词表，既得不到稳定文档近邻，也会把 BM25 的可解释性搅乱。成熟写法是 **两张虚拟表 + 应用层（或 SQL CTE）融合**——如 `sqlite-vec` + FTS5 + Reciprocal Rank Fusion（RRF，倒数排名融合）。

**对 fawai 的落点（现状，未等于放行新产品）：**

| 层 | 现状 |
|:---|:---|
| 笔记向量 | 已有可选 `vectors.sqlite`（sqlite-vec）；`retrieve` 可 `keyword ∪ vector` |
| lore FTS5 | **已落地**；有 `fts.sqlite` 时 retrieve 优先 FTS，否则子串 |
| 可读区正文 FTS / 文件名 | **已落地**（扫根 + 重建 + **watchfiles/轮询增量**）；拒 `/` 与主目录 |
| 混合融合 | 词法∪向量仍为并集排序，**尚未**正规 RRF |
| 仓向量搜 | 仍不做默认向量仓搜 |

因此：想要「词对不上也能找回」→ **继续嵌文档/笔记，不是嵌 FTS5 词条**；FTS5 负责钉死标识符与原文，向量负责同义与模糊回忆，统一打分即可。词级近邻扩查询只宜作可选辅路，不能当语义搜主方案。

## 3. fawai 现状落在哪一层

| 能力 | 是否「先建索引」 | 索引内容 | 查询形态 |
|:---|:---|:---|:---|
| `fs_grep` / `explore_search`（默认） | 否 | 无正文索引 | 每次 `rg` 或 Python walk |
| `code_symbols` / `code_map` | 是 | **符号**（类/函数名等），mtime 增量落盘 | 加载 JSONL 后**子串过滤**（非倒排 FTS） |
| lore 关键词 | **是（FTS5）** | KV+笔记倒排 | 有库则 MATCH；无库回落子串 |
| 可读区正文 FTS | **是（重建 + 增量监视）** | 文本文件正文 | `fts_search`；`fs_grep prefer_fts` |
| 文件名索引 | **是（重建 + 增量监视）** | 路径/文件名 | `name_index_search`；`fs_glob` 无通配可走 |
| lore 笔记向量 | 可选 | 嵌入 | 语义近邻，不替代词法 |

已有「索引」解决的是 **结构定位**；正文与知识库词法仍是 **扫**。这与速度分析里的 B2/B3、记忆分析里的 M3/M6 同因。

## 4. 能不能「像 Everything 一样先建索引」

能，但要拆成三条产品线，避免混成一个「万能索引」：

| 线 | Everything 类比 | 对 fawai 的收益 | 成本与风险 |
|:---|:---|:---|:---|
| **A. 路径/文件名索引** | Everything 主能力 | 宽根下列文件、按名找快；减轻 `fs_glob` 冷 walk | macOS/Linux 无 USN；须自扫 + FSEvents/`inotify` 或 mtime 轮询；跨平台设计要完整 |
| **B. 正文 FTS（仓内）** | 非 Everything 主战场；近 Zoekt/IDE | 少盲 `rg`、多轮试错；标识符/报错原文稳 | 初次建索、磁盘、增量一致性；中文分词；大树忽略规则须与 `fs_*` 一致 |
| **C. lore / 情节 FTS** | 个人知识侧 | 记忆「找不着」主杠杆之一 | SQLite FTS5 轻；与现有向量统一打分即可 |

**优先级建议（未放行；编号仅实施先后，后项仍属范围）：**

1. **P0 — lore FTS5**：语料小、痛点明确（记忆分析 P0）。  
2. **P1 — 仓内正文索引窄切口**：仅 `FAWAI_WORK_ROOT`（或显式检索根），工具如 `code_search`；查询仍可回落 `fs_grep`。  
3. **P2 — 路径元数据索引**：若宽 `READ_ROOTS` 仍要按名找，或工作树命名规范（见 §1.1）使「先名后文」成立；否则先收窄检索根（见 [检索根过宽仍放行](./检索根过宽仍放行.md)）性价比更高。  
4. **可选** — Zoekt 级正则预索引、会话内 grep 缓存、向量混合：可砍；砍后主验收仍靠 P0/P1。

**明确不建议：**

- 把 Everything 当「正文搜变强」的唯一药方（类型不对）。  
- 未收窄根就对 `/` 或整家目录建全文索引（体积与隐私爆炸）。  
- 用更重提示「请少搜」替代倒排。  
- 个人分身场首期上 Elasticsearch 集群。

## 5. 与「慢」三层的关系

见 [工具与文本检索速度对照.md](./工具与文本检索速度对照.md) §1：

| 层 | 预索引能治吗 |
|:---|:---|
| A 单次检索算力 | 正文/路径索引直接降；`rg --max-count` 早停是更便宜的半步 |
| B 检索产品能力 | FTS/混合检索少试错轮；符号升级另线 |
| C 工具闭环 LLM 税 | **几乎不治**；索引再快，每步仍付规划/反省秒级 |

因此：可以建索引，但 **不能指望「建完 Everything 式索引」单独治好体感慢**；须与动作段并行、早停、记忆路由一起看。

---

## 6. 一句话结论

**正常全文索引 = 分词后建倒排（term→文档/位置），查询读表不扫盘；Everything 主打的是路径元数据实时索引，不是正文 FTS。**  
fawai 已有符号落盘索引，缺的是 **lore/仓正文词法倒排**；方向上值得做，优先 lore FTS5，再工作根内 `code_search`，路径索引视宽根策略而定——且须另开议题放行，本篇仅对照。  
语义搜不要叠在 FTS5 **词表**上，应与 FTS5 **并列嵌文档/分块** 再混合打分（见 §2.2）；lore 笔记向量已具备雏形。
